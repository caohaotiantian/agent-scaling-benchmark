一、项目目标与边界

在统一 Benchmark 协议下，比较不同 Agent / 模型配置在 AI 辅助编程任务上的质量、Token 与耗时，服务 Agentic Scaling 横向对比与汇报。

做的事

会话抽库 → 筛选 → 生成可机评 case → 替换 Agent/模型跑测 → 写出综述表/通用表字段。

不做的事

自动无人审核发布正式集；Fusion 算法本体；完整 IDE UI；不设上限的全库无限扫描。

生产默认： Agent = openai_compat，模型 = GLM-5.2（经 OpenAI 兼容 API）， case 集 = auto-v0。Mock 仅存在于 tests/fixtures。

二、核心概念

术语 定义
Case 一条可评测任务：prompt + workspace 文件 + grader
Case set 一组 case 的目录名，如 auto-v0（候选）、prod-v0（发布）
Draft 从会话抽出的草稿，未必可跑
Run 一次完整实验：固定 case 集 + 一种 Agent/模型/算法配置
消融 Ablation 同一 case 集上跑多组配置并横向对比（对照实验矩阵）
主指标 task_success_rate = 成功数 / 有效 case 数（排除基础设施错误）

三、系统架构与数据流

数据层 llm_chat_records (MySQL) │ ▼ 构建层 extract-from-db → filter-drafts → generate-cases │ (+ audit / secrets-scan) ▼ Case 集 benchmarks/ai_coding/cases/auto-v0/ │ ▼ 执行层 materialize workspace → Agent.run → grade │ (case_workers 并行 / 失败重试) ▼ 报告层 summary.json · tables.json · report.md ablation_report.md（多配置对比）

仅生成用例（不做消融）

做到 generate-cases + validate/audit 即可停，不要跑完整 e2e_pipeline.sh（脚本末尾会消融）。

四、「消融」在本项目中的含义

这里的消融 = 对照实验：固定测评集，只改 Agent/模型（及算法标签），比较成功率、Token、耗时、相对基线收益。 与「删掉网络层做学术消融」不是同一操作，而是配置矩阵上的系统对比。

与设计一致： 「一行结果 = 同一 Benchmark + 同一 case set + 一个算法配置 + 预算档 + 一次 run」。 见 agentic-scaling-benchmark.html 设计结论。

生产矩阵 configs/runs/ablation-matrix.yaml 默认对比：

  • openai_compat + GLM-5.2
  • tool_loop + GLM-5.2

五、操作规程（你应当执行的命令）

5.1 只要生成测试用例

set -a && source .env && set +a

uv run python -m aibench extract-from-db \
  --output-dir benchmarks/ai_coding/cases/drafts-from-db \
  --limit 100 --max-cases 30 --require-gold

uv run python -m aibench filter-drafts \
  --input-dir benchmarks/ai_coding/cases/drafts-from-db \
  --output-dir benchmarks/ai_coding/cases/drafts-kept

uv run python -m aibench generate-cases \
  --input-dir benchmarks/ai_coding/cases/drafts-kept \
  --output-dir benchmarks/ai_coding/cases/auto-v0 \
  --max-cases 8 --audit --secrets-scan

uv run python -m aibench validate-cases --case-set auto-v0
uv run python -m aibench audit-cases --case-set auto-v0 --annotate

产物：benchmarks/ai_coding/cases/auto-v0/*.json

5.2 完整生产流水线（含消融）

./scripts/e2e_pipeline.sh --limit 100 --max-cases 8

5.3 已有 auto-v0 后只跑测

./scripts/run_benchmark.sh
# 或
uv run python -m aibench ablation --matrix configs/runs/ablation-matrix.yaml

5.4 --limit 与 --max-cases

参数 CLI 默认 e2e 脚本默认 含义
--limit 300（抽库） 100 DB 最多扫描多少行
--max-cases（抽库） 30 max-cases×3 最多写多少草稿
--max-cases（生成） 50 8 最多写多少最终 case

不传参则用默认，不会全库无限扫描。

六、配置体系（生产，无 mock）

agents/

openai_compat 单轮写文件；tool_loop 多步工具；shell 外部 CLI 包装。

models/

glm52（默认）、glm51、qwen37。Key/URL 来自 .env。

runs/

baseline.yaml 单次；ablation-matrix.yaml 多配置对比。

详细字段见 configs/README.md 与 docs/REFERENCE.md §5。

八、产物是什么、如何使用

8.1 生成阶段输出

  • drafts-from-db/ — 原始草稿
  • drafts-kept/ — 筛选后
  • auto-v0/*.json — 候选测试用例

8.2 单次 Run 输出

runs/AI-Coding-Assist__<时间>_<run_id>/

  • summary.json — 成功率、Wilson CI、分层、Token、成本估算
  • tables.json — 综述表一行 + 通用表关键字段
  • report.md / results.jsonl — 人类报告与明细

8.3 消融输出

runs/ablation_<时间>/ablation_report.md — 多行对比表（汇报首选）

目的 使用方式
汇报 / 选型 复制综述表列：算法、Agent、模型、成功率、耗时、Token、相对基线
归因 打开失败 case 的 result.json 与 report 失败诊断
复现 保留 manifest 中的 case_set_fingerprint 与配置路径
进总表 / 看板 程序读取 summary.json / ablation_summary.json / CSV

九、与初始设计文件的关系

agentic-scaling-benchmark.html

结果表设计报告：统一数据粒度、综述表、通用总表、确定性/偏好型任务、推荐落盘结构、落地阶段。 定义「表应该长什么样、一行代表什么」。

agentic_scaling_benchmark_tables.md

字段字典：综述表与通用总表每一列的含义与建议类型。 实现填表时的列名与语义权威来源。

本仓库实现 = 按上述合同跑实验并落盘填数： tables.json.overview_row ↔ 项目效果综述表； summary.json / general_row ↔ 通用结果总表核心字段； 主指标名显式为 task_success_rate（半确定性 AI 编程任务）。 无数据的列保持 null，不编造。
设计要求 实现映射
一行 = Benchmark + case set + 算法配置 + 预算 + run 一次 aibench run 或消融矩阵中的一行
综述表 ≤10 列 overview_row / ablation_report.md
通用总表细分列 summary.json 键 + general_row
落盘 runs/… runner 写出的标准目录

十、科学效度与并行

效度门禁

stub 必须 fail 污染检测 难度标签 指纹去重 Wilson 95% CI 分层成功率

并行层级

Case：run --workers / case_workers； 生成：generate-cases --workers； 消融：ablation --parallel。 

uv run python -m aibench audit-cases --case-set auto-v0 --annotate --fail-on-error
uv run python -m aibench run --workers 4
uv run python -m aibench ablation --matrix configs/runs/ablation-matrix.yaml --parallel 2
