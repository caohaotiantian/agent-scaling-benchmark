## 5. 未决问题

### 5.1 下一步做什么

三个候选，证据并列。**本会话没有得出结论，且中途改过一次立场（§7）。**

#### A · 锚点面板重标定

- **支持**：`HANDOFF §0.3` 列为「一切结论的前提」。面板确实反转 ——
  修复后实测 weak(openai_compat+GLM-5.1) **85.2%** > strong(tool_loop+GLM-5.2) **77.4%**，
  而 `spread`（最强−最弱）是 `select_cases` 的第一排序键，反转时它为负。
- **反对**：反转的成因已查明且不是能力差异 —— `openai_compat` 把**每个文件（含可见测试）
  整段贴进 prompt**（`openai_compat.py` 的 `file_blob`），`tool_loop` 只给 `Task:` 与
  `Workspace root:`。在 impl+test 两文件的扁平工作区里，前者拿到的是答案本身。
  重测同样三个锚点约 **6.3M token**，可预期仍反转。
- **未测**：换成构造单调的阶梯（同模型同适配器，只变 `max_steps ∈ {1,3,10,40}`）
  结果是否也单调。构造保证「能做的事是子集」，不保证结果单调。
  成本按历史实测每行 token 推算约 **8.7M**（`tool_loop`/GLM-5.2 实测 **107,035 token/行**，
  是 `openai_compat` 的约 70 倍，所以成本完全由步数上限决定）。
  0.4M 的探针设计见 `.agent/anchor-panel/plan.md`（**未执行**）。

#### B · 提高题目难度（隐藏测试）

- **支持**：`_revclean` 里 16/19 测试全可见；隐藏测试是项目实测过的、唯一移动过难度的杠杆：

  | 可见性 | strong 通过率 | mean p̂ |
  |---|---:|---:|
  | 全可见 | 90.3% | 0.527 |
  | 隐藏 2 条 | 55.9% | 0.380 |
  | 保留 3 条可见 | 52.7% | 0.344 |
  | 保留 1 条可见 | 47.3% | 0.312 |

  应用成本 **0 token**（`split_tests_for_hiding` 是纯确定性变换，已在代码里）。
- **反对**：上表**测于残废的 weak 锚点**（当时 42%，适配器修复后 85%），方向可能变。
  且 `hide_count=2` 当时把 11/31 推进「无人可解」。
- **未测**：修复后的 harness 上剂量响应是什么样。

#### C · 扩大题量

- **支持**：19 条对任何配对检验都少（见 5.2）。
- **实测的杠杆**：`llm_chat_records` 共 18,548 行，含 `"name": "edit"` 的 5,485 行
  （当前抽取谓词），含任一编辑工具的 **9,490** 行。差额 4,005 行里
  **`str_replace` 家族 0 条、纯 `write`/`file_write` 4,004 条**。
  `replay_file_versions` 对 `_WRITE_TOOLS` 只更新上下文（`seen[k] = body` 后 `continue`），
  **从不产出 FileVersion** —— 所以放宽 SQL 谓词单独做收益为零。
  让「read 之后整文件 write」也算一对 pre/post（`original[k]` 是 pre、写入的 body 是 post）
  是未做的改动，做了才吃得下那 +73%。
- **未测**：改了之后的真实产出率。

### 5.2 需要多少题 —— 现有数据不足以回答

已发布的配对比较，全部 n=31：

| 对比 | 不一致 | 95% 区间 |
|---|---:|---|
| tool_loop: GLM-5.2 vs GLM-5.1 | **25.8%** | [13.7%, 43.2%] |
| tool_loop: GLM-5.2 vs GLM-5 | 19.4% | [9.2%, 36.3%] |
| tool_loop: GLM-5.2 vs Qwen3.7 | 19.4% | [9.2%, 36.3%] |
| tool_loop: GLM-5.2 vs Deepseek | 6.5% | [1.8%, 20.7%] |
| bare_model: GLM-5.1 vs Deepseek（19 条清洗集） | 5.3% | [0.9%, 24.6%] |
| **同一模型、不同轮次** | **12.9% / 19.4%** | ← 纯噪声 |

两件事同时成立，且互相纠缠：

1. **区间宽到不能支撑任何样本量结论。** 同一份数据按下界算「检测 3pp 不可能」，
   按上界算「检测 10pp 需 192 条」。
2. **模型间不一致率（19–26%）与同模型轮间不一致率（13–19%）量级相同。**
   信号与噪声底难以分辨。这与 `HANDOFF §0.5` 已记的现象一致
   （同一对比单次 p=0.0312「显著」，三次 p=0.167 不显著）。

**没有做过的测量**：agent 轴（`openai_compat` vs `tool_loop`）的配对不一致率。

### 5.3 `no_discrimination` 判据是否成立

- 修正后的估计量在零假设下 **P(r_pb > 0.15) ≈ 0.35**（修正前 0.55）。
  纠偏把假阳率从「过半」降到「三分之一」，不是降到「小」。
- 真 ρ=0.5 时的功效约 0.84 → 似然比约 2.4。
- **阈值 0.15 的来源在代码和文档里都找不到推导。** 如果它当初是对着旧的被抬高的
  零分布调出来的，纠偏之后它实际变严了。
- r_pb 的零分布 sd = 1/√(n−1)，而各 case 实测到的 run 数不同（4~9），
  **同一个阈值对不同 n 是不同严格度的尺子**。

## 7. 本会话的两次方向判断失误

记下来是为了让后来者校准对本会话输出的信任度。**数据与代码改动经过多方复算，方向判断没有。**

### 7.1 高估产量三次，每次都是没把链条走到末端

| 估计 | 实测 | 错因 |
|---|---|---|
| 差分验收可产 214 条 | 7–9 条 | 把幸存者上量的条件概率乘到未过滤的全语种池 |
| 兄弟文件是最大杠杆 | 只回收 12 条，是最小的 | 只看「缺什么」，没查兄弟在不在 trace 里、闭包完不完整 |
| 放宽 SQL 谓词 +73% | 收益为零 | 没查回放对 `write` 从不产出 FileVersion |

### 7.2 用单一对比推翻整条路线

会话末尾，本会话据「清洗后 19 条里模型间只有 1 条不一致（5.3%）」论证
「锚点面板不在关键路径上，题目天花板才是瓶颈」。

**这个论证有两处错误：**

1. **挑了不一致率最低的那一对。** 所用的
   bare_model / GLM-5.1 vs Deepseek 是全部已发布配对里最低的一对；
   tool_loop 下的模型间不一致率是 19.4–25.8%（见 5.2）。
2. **把 5.3% 当精确值代进 `plan-sample-size`**，据此断言「3pp 需要 434 条」。
   1/19 的 95% 区间是 [0.9%, 24.6%]，27 倍跨度，不支撑任何样本量结论。
   这正是 7.1 同一类错误的第四次。

「面板反转的成因是任务呈现差异」这一条诊断本身经代码核对成立（`openai_compat` 贴文件），
**但由它推出的方向结论不成立**。
