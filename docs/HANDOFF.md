## 0.-1 全量重建（2026-08-12）

### 起因：read 工具的页脚被当成了文件内容

`extract_files_from_tool_text` 把 `<content>` 里的一切当文件，**连工具自己那行页脚一起**。
穷举整池 23,868 个重建文件的每一行，页脚只有五种形状，**98.0% 的文件带一个**：

```
17010  (End of file - total N lines)
 5954  (Showing lines N-N of N. Use offset=N to continue.)
  231  (File has more lines. Use 'offset' parameter to read beyond line N)
  202  (Output capped at N KB. Showing lines N-N. Use offset=N to continue.)
    1  (Output truncated at N bytes. Use 'offset' parameter to read beyond line N)
```

两重后果：页脚让 Python 必然 `ast.parse` 失败，素材在进池前被 `require_parse` 删掉；
且 `pre` 的三种来源（完整读 / 窗口读 / 从未读过）不被区分，
**「stub 是 trace 找到时的文件」这条立论对旧素材只有 35% 成立**。

`_revclean` 19 条里 2 条由此而来：`rev-461e8d91390e3915` 的 stub 是 190 行文件的前 40 行、
断在 `success: false,` 中间；`rev-d098848d56868e13` 的 stub 用 `node --check` 报
`SyntaxError: Unexpected token 'of'` —— **它的 stub 门禁是靠文件加载不了通过的**。
**所以那 19 条实为 17 条。**

`audit-cases --case-set _clean2026` → **45/45 通过**，指纹 `c8e47df626a689a9`。

### 产量漏斗（实测）

```

  → 137 次生成尝试 → 133 条用例（含 --resume 补回 35 条）
```

**去重键是 `(pre,post)`，不是源文件。** 两者差 9 条，而且两个方向的错误都真实存在：

- **不去重不行**：14 个同源分组里 **8 个的 `(pre,post)` 逐字节相同** ——
  `config_diff_analyzer.py` 出了 8 条、`medium_search.py` 7 条，全是同一个缺陷的副本，
  只有模型写的测试与题面不同。当成 8 道题就是虚报。
- **按源文件去重也不行**：`settings.py` 那 6 条里有 **4 个不同缺陷**，`__manifest__.py` 有 3 个。
  按文件压成 1 条会扔掉真题。第一版就是这么做的，少算了 9 条。

`§0.7` 早就写明「按 `(pre,post)` 内容去重后计数」——第一版套用了 `§6.0` 那条
「按源文件去重」的规则，而那条针对的是**多轮构建跑同一批草稿**的重复，总体不同。
这与 §5.12.1 是同一类错误：把一个总体上的规则搬到另一个总体。

**残余聚簇要如实报，但不能靠删题解决**：去重后仍有 7 个文件各贡献多个不同缺陷
（`settings.py` 4 个、`build.py` / `models.py` / `__manifest__.py` 各 3 个）。
它们是不同的题，但共享同一份文件上下文，所以模型表现相关。
配对检验遇到聚簇的正确处理是**报告并按簇分析**，不是丢弃样本 —— 丢弃既损功效又不解决相关性。

**但两条否定结论同样重要，它们排除了两条看起来更省事的出路：**

1. **剔掉那些用例救不回来。** 只剔 both_fail 里的 13 条 → 剩 32 条，不一致 3/32 = 9.4%，

   两种口径都报，因为后者会剔掉一条 discordant——那是被测指标的分子。哪种都不高于噪声底。
2. **提高度量粒度也救不回来。** 连续分 `test_pass_ratio` 把逐条有差异的用例提到 17/45，

   同口径（两边都按三轮取均值）二值是 8/45，所以分辨率是 **2.1 倍**，翻倍仍无方向。

> 平均 `test_pass_ratio` 有两个口径：全部 270 次运行 **0.754**，只算 175 次失败运行 **0.62**。
> 前者不能当作「模型在没做成的题上做对了多少」来引用。

## 0.0 用 opencode 替代 tool_loop 的实测结论（2026-08-11）

新增 `opencode` 适配器（`src/aibench/agents/opencode.py`，见 REFERENCE §12.4），
把 opencode CLI 作为子进程驱动。**同一批 19 条用例（`_revclean`）、同两个模型、各 3 轮**：

| 口径 | GLM-5.1 | Deepseek-V4-Flash | 轮间极差 | 逐条翻转率 | token 合计 |
|---|---:|---:|---:|---:|---:|
| `bare_model` | 89.5 / 89.5 / 89.5 | 78.9 / 84.2 / 84.2 | 0.0 / 5.3pp | 0.0% / 15.8% | 0.71M |
| **`opencode`** | **100 / 100 / 100** | **100 / 100 / 100** | **0.0 / 0.0pp** | **0.0% / 0.0%** | 7.41M（**10.5×**） |

对照 `tool_loop` 在 `_revmixed` 上的历史数字：翻转率 25.8%–32.3%、轮间极差 12.9–16.1pp。

### 三条结论，强度不同

1. **不稳定性确实来自 `tool_loop`。** 换成真实 agent 后，两个模型三轮**逐条完全一致**。
   §5.14 记的「五轮互相矛盾的排名」到此可以结案：那是仪器的方差，不是模型的差异。
2. **`_revclean` 对真实编码 agent 零区分度。** 114 次 case-run 全过，
   每一对配对检验的不一致对都是 0。**这不等于两个模型一样强** —— 天花板掩盖差异，
   正是 §1 说的那件事。19/19 的 Wilson 95% 区间是 [83.2%, 100%]。
3. **脚手架值 +10.5pp（GLM-5.1）/ +17.5pp（Deepseek），代价是 10.5 倍 token。**
   这是本项目第一次在同一批用例上把「模型」与「模型+真实 agent」分开量出来。

### 先排除了仪器故障才敢这么读

不跑 agent、直接判分原始工作区：**19/19 全部失败**。所以 100% 不是「判分永远通过」。
114 次运行里 `reward_hack` 0 次、`empty_patch` 0 次，写入的文件全是 impl，**没有一次改测试**。

### 0.0b 隐藏测试：难度旋钮成立，区分度旋钮不成立（2026-08-12）

假说：**区分度 = 评分信号与 agent 可观测信号之间的信息差。** 差为 0 时任何勤奋 agent 得满分。
它一个变量解释了本项目四条散落的发现（隐藏测试是唯一动过难度的杠杆；做大做真无效；
题面去泄露无效；`bare_model` 在同一批用例上有区分度而 opencode 没有）。

**剂量响应**（`_revclean` + `protected_paths`，GLM-5.1 × opencode，2 个完整重复；
第 3 轮因网关不可达报废，45 次运行挂满 900s 零模型调用）：

| 隐藏条数 | 通过率 | 两轮都解出 | 轮间翻转 |
|---:|---|---:|---:|
| 0 | 100% / 100% | 19/19 | 0/19 |
| 2 | 73.7% / 68.4% | 13/19 | 1/19 |
| 4 | 68.4% / 57.9% | 11/19 | 2/19 |

**区分度实测**（hidden=4，2 模型 × 19 条 × 3 重复，6 行全 19/19 有效）：

| | GLM-5.1 | Deepseek | 配对不一致 | McNemar p |
|---|---:|---:|---:|---:|
| 全 19 条 | 63.2% | 68.4% | 1/19 = 5.3% | 1.000 |

而**同一模型三轮之间**的自翻转是 GLM-5.1 **15.8%**、Deepseek 5.3%，
且那条唯一「跨模型不一致」的用例正是两者对自己都会翻转的那一条。
**跨模型差异完全被自身噪声解释，实测区分度为零。**

三条结论：**① 信息差确实是难度旋钮（0 成本）；② 难度 ≠ 区分度，两个模型一起下移；
③ 在本语料上提难度买到的是方差不是信号**（hidden=0 时逐条完全确定，hidden=4 时开始翻转）。

**推论：单文件缺陷修复这一任务类型，在任何难度下都分不开这两个模型。**

新增门禁 `hidden_test_requires_unknowable_symbol`（§14）：隐藏测试索要的符号若在
shipped 文件 / 可见测试 / 题面里都不出现即判不合格 —— 这类用例谁都解不出，
在通过率上长得像难题却区分不了任何东西。三个已发布集合合计 155 个符号**零命中**。

### 0.0c 判别实验：用例**有**刻度，缺的是题量（2026-08-12）

上一节留下两个互斥解释（用例没刻度 / 这两个模型本来就一样）。用网关上最宽的能力差
（最老的 GLM-5 vs 最新的 GLM-5.2）同集合同剂量各 3 重复，6 行全 19/19 有效：

| | GLM-5.2 | GLM-5 | 配对不一致 | McNemar p |
|---|---:|---:|---:|---:|
| 全 19 条 | 68.4% | 52.6% | **3/19 = 15.8%** | 0.250 |

**方向 3:0，从无反向** —— 与 GLM-5.1 vs Deepseek 那轮（1/19 且被自身噪声解释）截然不同。
**用例有刻度，只是刻度太粗。**

逐轮拆开：2 条是 GLM-5 自翻转（1/3 通过）→ 属**可靠性**差异；
1 条是稳健能力分离（GLM-5.2 3/3，GLM-5 0/3），而它正是上一轮中档模型都会自翻转的那条 ——
一条真正落在能力前沿上的用例。

**新发现的一条轴：可靠性，而且它比通过率更早显形。**
自翻转率 GLM-5.2 = **0/19**（三轮逐条完全一致），GLM-5 = 3/19。

> ### ⚠️ `unsatisfiable_imports` 的判定依赖工作目录（现存缺陷，本轮未修）

> 顶层 import 就被判为「可满足」。语料里 `import src...` 与 `import tests...` 正好撞上

>
> 同一批草稿、同一个解释器，仅因调用方式不同：
>
> | 条件 | 存活 Python 对 |
> |---|---:|
> | 仓库根在 `sys.path` 上（`python -c`、heredoc、`PYTHONPATH=.`） | 24 → 23 |
> | 不在（`python scripts/x.py`，`sys.path[0]` 是脚本目录） | **21 → 20** |

> ### ⚠️ 本节的结论在 2026-08-12 被实测推翻，两处都错
>
> **错误一：「`replay_file_versions` 从不为 `write` 产出 FileVersion」——不成立。**
> `file_versions.py` 的 `pre=original.get(k, base)` 会回落到 `base`（即 `seen[k]`，
> 可能由 `write` 写入）。实测两个最小 trace：
>
> ```
> write a.py("x = 1\ny = 2") → edit(x = 1 → x = 99)
>   ⇒ FileVersion(pre='x = 1\ny = 2\n', ...)        ← pre 出自 write 参数
> read a.py("old = 1") → write(整文件重写) → edit(...)
>   ⇒ FileVersion(pre='old = 1\n', post=重写+编辑后) ← 整次重写被并进「缺陷」
> ```
>
> 现有池的 737 个 pair 里，**278 个的 `pre` 完全没有 read 页脚**，其中 182 个的文件
> 在该草稿的 `context.files` 里从未出现过 —— 那些「缺陷」是模型自己写的代码里的问题。
>
> **错误二：「+73% 的语料」是行数，不是素材。** 按该改法实现一版实测：
> `write ∧ ¬edit` 片（3,961 行）跨全期取 800 行出 **3 对**可用，全语料外推约 **15 对**，
> 对现有约 92 对的可用池是 **+16%**。机制是工程师用整文件 `write` 写
> `.md` / `.json` / `.xml` / `.cj`，用 `edit` 改代码。
> 更宽的分层样本（2 天分桶跨 40 天）在两个片上都得 0 可用，
> 但那是 0/6 个过语言门的 Python 对，在 §0.7 实测 74% 的 import 门淘汰率下
> P(0 of 6) ≈ 0.16 —— **「零」同样没有被证明**。结论是「小、未证实、被语言门主导」。
>
> **真正挡路的是别的东西**：read 工具的页脚被当成文件内容保存了下来。
> 详见 `docs/REFERENCE.md` §14.3.9 与 `.agent/trace-yield-expansion/plan.md`。

**放宽 SQL 谓词单独做，收益为零。** `replay_file_versions` 对 `_WRITE_TOOLS` 只更新上下文
（`seen[k] = body` 后 `continue`），从不产出 FileVersion。真正的杠杆是让「read 之后整文件 write」
也算一对 pre/post —— `original[k]` 是 pre、写入的 body 是 post，现在被直接丢掉。
改这一处才吃得下那 +73% 的语料。

## 2. 已交付

### 2.1 分层契约（`src/aibench/tiers.py`）

用例按「结构上强迫求解者做什么」分层，每层配机器可检不变量：

| 层 | 能力轴 | 关键不变量 |
|----|--------|-----------|
| T1 直接修复 | — | ≤3 文件，允许题面/注释给出缺陷位置（地板锚） |
| T2 定位修复 | A1 | 题面无机制泄露，stub 无 BUG 标记 |
| T3 隐藏规格 | A1,A5,A6 | ≥2 隐藏测试函数 + 参考解 + 保护可见测试 |
| T4 上下文检索 | A1,A2,A5,A6 | ≥5 文件 + ≥1 干扰文件 |
| T5 跨文件自修复 | A1–A6 | 参考解触及 ≥2 文件 + ≥4 隐藏测试函数 |

层级由**源 trace 的过程信号**推导（`extract/trace_signals.py`）：检索次数、触及文件数、测试运行次数、`test→edit→test` 修复轮次。分布因此继承真实生产任务的难度构成。

`settle_tier` 从 T5 逐层下探，**标签描述产物而非请求** —— 材料只够 T3 就标 T3，绝不虚标。

### 2.2 消灭捷径

| 机制 | 作用 |
|------|------|
| `grader.hidden_tests` | agent 结束后才注入工作区，消灭"读测试反推答案" |
| `grader.protected_paths` | 判分前比对字节，改测试判 `reward_hack` |
| 评分干扰检测 | 挡住绕过路径：注入 conftest 猴补丁、pytest.ini deselect、新文件塞 skip 标记 |
| `solvability_gate` | **参考解必须通过**，与 stub-fail 成对构成难度上下界 |

### 2.3 度量

- **pass@k**：k 次独立采样折成一行落盘（保持一 case 一行，下游三个消费者无需改动）。产出 `pass_at_1` / `pass_at_k` / `pass_pow_k` / `selection_hit_rate`。`success_rate` 口径不变，k=1 时与旧行为逐字节一致
- **成本轴**：`cost_curve`（档位取自实测 token 分布）+ `token_amplification`
- **McNemar 配对检验**：同一 case 集上的配对比较，比各自的 Wilson CI 灵敏得多
- **`plan-sample-size`**：按实测不一致率反推所需题量

### 2.4 校准与选题

`calibrate-cases` 用锚点面板实测每条用例的 `p_hat` / `spread` / `point_biserial` / `flaky`，
淘汰送分题、坏题、噪声题；`select-cases --tier-quota` 按层配额组集。

支持增量（`--reuse-from`，case 与面板都未变才复用）与并行（`--parallel`）。

**锚点面板必须能施展被测层级的能力轴** —— agent 用 `capability_axes` 声明，
`calibrate-cases` 开跑前核对，不匹配直接拒绝。

### 2.5 其他

- 多语言：`languages.py` 收拢 per-language 知识，注册 Python(pytest) 与 JavaScript(`node --test`)，**只注册本机能真跑的语言**
- `compose-cases`：从已验证用例合成 T4 检索用例，两道门禁由构造保持
- 消融行级容错、真机 CI（缺 secret 时跳过而非失败）

## 5. 经验教训

### 5.1 最重要的一条：静默的错误结论比崩溃危险得多

本次修的缺陷里，**没有一个会让程序崩溃**。它们都产出了看起来完全正常的数字：

- model 解析 bug → 报告如实写着"GLM-5.1 vs GLM-5.2"，实际跑的是同一个模型
- tool_loop 切片 bug → agent 轴数据一直存在，只是全部是 infra_error
- 全失败实验 → 显示 `0.0%`，读起来像"这个 agent 很差"

判据：**任何"沉默地给出错误答案"的路径，优先级高于"大声崩溃"的路径。**

### 5.2 我自己犯过三次同类错误：对比被污染

| # | 错误 | 后果 |
|---|------|------|
| 1 | 拿 27 条**筛选后**用例对比 126 条全量 | 合成效果看起来是大成功 |
| 2 | 把无参考解的**坏题**混进"难题"组 | 得出"修复跨度 <15% 是主因"，差点据此加错门禁 |
| 3 | 用**测不了该能力**的面板读 T4 数据 | 弱锚点通过率反而 +24pp，看起来像好消息 |

三次的数字表面都说得通，**只有回到机制才发现问题**。教训：任何对比先问"两组除了我关心的变量，还差什么"。

### 5.3 豁免条款是缺陷的藏身处

`check_reference_solution` 有一行"没有参考解就跳过"。结果：**最没能力自证可解的用例，恰恰是唯一没被要求自证的**。18 条无人能解的用例里 16 条走了这条豁免。

同类：`generate_case` 拒绝无参考解的输出后，调用方回退到启发式路径，而它造不出参考解 —— 于是安静地产出了刚被拒的东西。

### 5.4 同一个守卫抄三份，必然漏一份

`materialize_workspace` 和隐藏测试写入都有路径逃逸防护，`check_reference_solution` 没有。
生成的用例带 `/home/code/...` 绝对路径，参考解被写到**宿主机文件系统**上。已收进 `workspace.safe_relpath`。

### 5.5 能力定义与度量工具必须匹配

T4 测检索，但单轮 agent 把整个工作区贴进 prompt —— 对它而言没有"检索"这回事，干扰文件是白送的可用代码。
**施展不了某条轴的成员不会在那条轴上得低分，它得的是另一回事的分。**

已做成硬检查（`capability_axes` + `unfit_anchors`），因为这类错误从数字上看不出来。

### 5.6 门禁会把「难」和「坏」一起筛掉，于是集合必然变简单

这是 2026-08-05 复盘出来的、比 §5.1 更隐蔽的一层：

审计**通过**的 98 条 mean p_hat 0.849、ctx LOC 中位数 28；审计**失败**的 28 条
mean p_hat 0.077、中位数 **388**。也就是说，这套语料里「大而真实」与「不可验证」高度重合，
门禁每删掉一条坏题，同时也删掉了这个集合仅有的难度来源。

**所以「送分题占比高」不是生成器不肯造难题，是只有小题能活着通过可解性门禁。**

推论：**在能把「工作区跑不起来」与「任务难」分开之前，任何提升难度的努力都会被门禁抵消**——
它只会把用例从「小而保留」挪到「大而被丢」，而两种结局在 p_hat 上都读作「难」。
判据：先买测量能力，再谈难度。

### 5.7 我又犯了第四次「对比被污染」，而且是在援引该教训的同一份文档里

§5.2 记了三次。第四次：为了给「合成不解决问题」找证据，我引用了
「合成集送分率 66.7% vs 基线 63%」—— 前者是**筛后 27 条 + 检索面板**，
后者是**未筛 126 条 + 单轮面板**，同时踩了 #1 和 #3。

而干净的配对数据**当时就躺在磁盘上**（同面板、同 27 条宿主，Δ=−0.009），我没去算。

教训升级：**「先问两组除了我关心的变量还差什么」不够，还要先问「有没有现成的配对数据」。**
凑一个方向正确的数字，比没有数字更危险。

### 5.8 报出去的数字要能被独立复算，否则会连错两次

本次我报给用户的关键数字错了两轮，都是评审复算查出来的：

| 我报的 | 实际 | 错因 |
|---|---|---|
| 「24/28 是坏工作区」 | **3** | 把 21 条无参考解用例重复计了一次 —— 它们的参考解从未运行过，谈不上「工作区被证明是坏的」 |
| 「`de2b33a` 已强制参考解」 | 应看 **`7a9b4e1`** | `de2b33a` 只堵 LLM 路径；auto-v0 建于两者之间，那 21 条走的是启发式回退 |

共同点：**都是用 shell 快速统计得来的，没有按 case_id 去重、没有区分数据集边界**。
判据：任何要写进结论的计数，都必须按实体 ID 去重并说明取自哪个集合；
`grep | wc -l` 只能用来找线索，不能用来下结论。

### 5.9 语料选错了，"0 破坏" 只证明你没测到

2026-08-06 消毒改造里我连续两轮报出干净数字，两轮都被评审推翻：

| 我报的 | 我用的语料 | 评审用的语料 | 真实结果 |
|---|---|---|---|
| 「改 33 / 坏 0」 | 只有 Python | 加上 1355 个真实 .js | JS 改 19 **坏 17（89%）** |
| 「JS 800 / 3 / 0」 | 800 个 .js | 7190 个 .js | 改 20 **坏 12（60%）** |

两次的数字对我跑过的东西都是真的，对问题都是假的。第二次尤其危险 —— 我已经知道 JS 是弱点，
特地去测了 JS，只是**语料小到不足以区分新旧两条规则**。

判据：报「0 缺陷」之前先问 **这个语料能不能把我改前和改后区分开**。
把改动前的实现也跑一遍同一语料 —— 如果两者都是 0，那说明语料没有区分力，不是代码没问题。
（正确做法的样子：最终一轮我用 8000 个 .js 复测，同时验证旧规则在同语料上确实会坏。）

### 5.10 监控一个不可能变化的信号，等于没监控

同一天犯了两次，形状完全一样：

1. 等 workflow 完成，轮询 `grep -c completed journal.jsonl >= 6`。但那份 journal 只写
   `type:"started"` 和 `type:"result"`，`completed` 只在 agent 正文里偶然出现 2 次。
   **条件永远不可能满足**，两个 shell 空转了 18 小时。
2. 等生成进度，轮询输出目录里的文件数。但 `generate-cases` 是**跑完才统一落盘**的
   （`cli.py:772`），目录在整个运行期间必然是空的。监控了一小时全是 0，
   我一度以为任务挂了，实际它一直健康（日志里已有 87 条）。

第二次还叠加了一层：Python 的 stdout 在重定向到文件时是**块缓冲**的，
所以头一个小时日志是 0 字节 —— 外部看起来像死了，其实只是没 flush。

判据：**装监控之前，先手动让那个信号变化一次。** 变不了就说明选错了观测点。
另外，harness 对它自己启动的后台任务本来就有完成通知，
再去轮询是纯浪费 —— 那两个空转的 shell 从一开始就不该存在。

**第五次（2026-08-07）：把「我发出了启动命令」当成「进程在跑」。**
`setsid nohup ... & ; echo "launched pid=$!"` —— macOS 没有 `setsid`，命令立刻失败，
但那句 `echo` 照样打印了 PID，我照样报告「已启动」。**`$!` 是 shell 记的最后一个后台 PID，
不是「那个程序」的 PID，命令找不到时它也有值。** 15 分钟后回来看，日志 0 行。

同一天还自己杀过一次：`nohup ... &` 和等待循环写在**同一条** Bash 命令里，
该命令超时被杀时整个进程组一起没了；而 `generate-cases` 是跑完才统一落盘（§5.10 第 2 条），
所以输出目录空空如也，什么都没留下。

判据升级为两条，缺一不可：
1. **启动之后、汇报之前，用独立的一次 `pgrep` 确认进程真的在。** 打印的 PID 不算证据。
2. **启动命令和等待命令必须分开写。** 等待那条超时被杀，不能连累被等的进程。

**第六次（2026-08-07）：看门狗把自己数了进去。**

```sh
until ! pgrep -f "extract-from-db" >/dev/null; do sleep 30; done
```

这条循环所在 shell 的**命令行本身就含有 `extract-from-db` 这个字符串**，
于是 `pgrep -f` 每次都匹配到自己 —— **它在等自己消失**。两个这样的循环空转了半小时，
而被等的抽取其实早已成功（写出 3,312 条草稿）。我不但没拿到结果，还向用户报告了「仍在跑」。

这一次的代价比前五次都大：前五次只是浪费时间，这次让我**错过了一个已经完成的结果**，
并据此做出了错误汇报。

判据补第 3 条：**`pgrep -f <pattern>` 的 pattern 不能出现在发起它的那条命令里。**
可行写法：
- 用不会自匹配的字符类：`pgrep -f "[e]xtract-from-db"`
- 或按 PID 等：启动时记下 PID，`while kill -0 $PID 2>/dev/null; do sleep 30; done`
- 或干脆不写等待循环 —— harness 对自己启动的后台任务本来就有完成通知（§5.10 已经说过一次）。

**第四次（2026-08-07）：这次是我自己造的。** `--reverse` 分支直接 `return` 构造好的用例，
从没走到普通路径那句进度打印 —— 而那句打印的注释恰好写着它为什么存在
（"LLM generation can take minutes per draft; without this the command looks hung"）。
整轮运行日志停在 114 字节。写进 §5.10 两次仍然再犯，说明**写下来这个动作本身不起作用**；
唯一真正起作用的是花三十秒手动让信号动一次。

### 5.10.1 让 JSON 解析器替你判断失败原因，它会给出错误的原因

反向构造第一轮：22 条可用草稿只出了 2 条，20 条失败报成
**10 次 `Expecting property name` + 8 次 `no JSON object`**。
两个都指向「模型输出格式坏了」。对着一条失败草稿插桩打一次真实请求：

```
finish_reason: length
reasoning_tokens: 4096   content: len=0   reasoning_content: len=17840
```

**根因只有一个：输出预算不够。** 模型把 4096 token 全花在推理上，没来得及作答；
客户端于是回退到 `reasoning_content`，把一篇英文推理稿喂给 `json.loads`。
不含花括号的散文 → "no JSON object"；含代码花括号的散文 → 首`{`/尾`}`切片截到垃圾
→ "Expecting property name"。同一条草稿把预算提到 16384，`finish_reason: stop`，
3996 token 内返回合法 JSON。修复后同批数据 **0 次失败**。

两条判据：

1. **失败信息若来自下游解析器，它描述的是症状不是原因。** 上游截断、超时、限流、
   空响应，到了解析器眼里全长一个样。插桩打一次真实请求比读十条错误日志有用。
2. **别让「取不到 A 就用 B」跨越语义边界。** `content or reasoning_content` 这个回退
   在网关把答案放 reasoning 里时是对的，在**响应被截断**时是错的 —— 它把
   「模型没答完」变造成「模型答得不合法」。现在只在 `finish_reason != "length"` 时回退，
   截断则抛 `TruncatedAnswer`，把预算翻倍重试（上限 49152），且**故意不可重试** ——
   用同样的预算重跑只是重复付钱。

### 5.11 规模探路批：花一次生成的钱，买「只在规模上暴露」的缺陷

2026-08-06 跑了一批 600 条的生成（不做校准，只做审计），目的有二：
看产线在 10 倍规模上的行为，以及把小样本上的结论收窄。**四个缺陷只有它能发现**：

| 缺陷 | 12 条探路批 | 600 条探路批 |
|---|---|---|
| `'str' object has no attribute 'get'` 把用例推去弱路径 | 0 次 | **53 次**（回退首因，超过 JSON 解析失败的 33 次） |
| secrets 误报（`apiKey: string` 这类 TS 声明） | 0 条 | **25 条**，直接让 `--secrets-scan` 判定不 clean |
| case_id 重名静默覆盖 | 0 次 | **23 个 id 重复、32 次写入被吞** |
| `--max-cases` 不约束成本 | 看不出来 | 为 **810** 条草稿付费只留 600 |

判据：**在把流水线放大 10 倍之前，先花一次生成的钱跑一遍 10 倍规模。**
单测和小批量都覆盖不到这一类 —— 它们全都来自真实数据的长尾形状
（真实配置文件、真实 TS 源码、生成器的偶发 id 碰撞）。

### 5.12 相关不等于因果，判据是「干预之后还在不在」

生成端找难度杠杆，两条候选都走完了完整流程，**两条都是相关但不因果**：

| 杠杆 | 观察数据里的相关 | 干预之后 |
|---|---|---|
| 用例做大做真 | 直觉上强 | corr **+0.07**（方向还相反）；合成 Δ **−0.009** |
| 题面点名被修函数 | **+0.201** p_hat 差，p<1e-8 | 点名率压掉 12.8pp，**难度不动**；组内 delta 掉到 +0.081 |

第二条尤其值得记：它在 `auto-v0` 上的相关性极强且高度显著，
但那是因为**「点名」与「这是一道模板题（kata）」在该集合里完全混淆** ——
不点名的 kata 用例有 **0 条**。所以那 +0.201 很可能一直在测「题简不简单」，
而不是「题面泄不泄露」。压掉点名率，等于换了个说法描述同样简单的题。

判据：**一个因素能不能当杠杆，只有对它做干预、再重新测量才知道。**
观察数据上的相关性（哪怕 p<1e-8）不构成证据。
本项目已为此付出两次完整的建集+校准循环 —— 这是可以接受的代价，
因为**排除一条错误路线的价值，等于省下沿着它继续投入的全部成本**。

### 5.12.1 从一个总体上测出来的「不值得做」，不能直接搬到另一个总体

反向构造的计划把「依赖闭包」写进了 Non-goals，理由是**实测只值 4/575 条**。
那个 4/575 是在**正向生成**的用例上测的 —— 那条路上 LLM 写的是自包含代码，
本来就没什么外部依赖可闭合。反向构造的总体完全不同：**每个 stub 都是真实仓库里的真实文件**。

实测 22 条反向用例的门禁结果：

| 结果 | 条数 | 含义 |
|---|---:|---|
| stub 与 gold **都跑不起来**（`exit=2`） | **9** | 工作区坏了，不是难题 |
| `stub_passed_grader` | 6 | 测试没抓住缺陷 —— **门禁按设计工作** |
| `reference_solution_failed` | 1 | 测试在 gold 上也挂 |
| 全部通过 | **6** | |

那 9 条缺的模块分两类：**第三方**（`pptx`×7、`numpy`×3、`torch`×2、`PIL`×2、`av`）
与**同仓库兄弟模块**（`pypto`、`context_memory`、`obstacle_avoidance`、`jiuwenclaw`、`torchtitan`）。
后者正是依赖闭包问题，占掉 41% 的产量。

判据：**引用一个「实测不值得」的结论时，先问它是在哪个总体上测的。**
换了总体，那个数就得重测。这条和 §5.12（相关不等于因果）是同一类错误的两个方向 ——
前者是把相关当因果，这里是把一个条件分布当成了无条件结论。

### 5.12.2 反向构造的产量漏斗：瓶颈不在解析，在语言覆盖

一直以为重放定位率 26.2% 是主要损耗。在 998 条草稿上实测，**定位率是 77.8%**
（`edits_applied 2534 / edits_seen 3257`）—— 早先那个数来自另一个样本，不能代表这批。
真正的漏斗是：

| 环节 | 数量 | 备注 |
|---|---:|---|
| 有编辑的文件候选 | ~1119 | |
| **因语言未注册被丢弃** | **849 (76%)** | cpp / h / rs / md …… 本机跑不了 |
| 因 pre 或 post 解析失败被丢弃 | 200 | |
| 存活的 pre/post 对 | 70 | |
| **其中单文件工作区能满足 import** | **27 (39%)** | |
| 落到草稿层面 | 19 条 / 998 (1.9%) | |
| 再乘测试质量通过率（实测 1/6） | **≈ 3 条有效用例** | |

**结论：反向构造的产量天花板由语言覆盖决定，不由 trace 解析决定。**
真实工程师改的文件里 76% 是这个 harness 跑不了的语言。
按当前各级比率，整个语料（约 5,485 条含编辑的记录）大约只能产出**十几条**有效用例，
离消融实验所需的 153 条（§6.5）差一个数量级。

要提高，只有三条路，按杠杆排序：

1. **增加可执行语言**（cpp/rust/go）—— 直接冲着那 76% 去，但必须是**真能跑的工具链**，
   否则就是 §2.5 那个坑：跑不了的语言让坏题伪装成难题。
2. **依赖闭包** —— 把 trace 读过的兄弟模块一并放进用例（快照已经在 `seen` 里了），
   冲着 import 那 39% 去。
3. **装一小组常见包**（numpy/pandas/requests/matplotlib）—— 便宜，但会改变评测环境，
   已发布的校准结果需要声明环境版本才可复现。

### 5.13 端到端测试发现单元测试发现不了的

JavaScript 那条端到端用例逼出两个 bug：隐藏测试文件名 `clamp.test_spec.mjs` 不匹配 node 的发现规则（静默不跑）、tally 正则只认 TAP 的 `# pass` 而 node 默认输出 `ℹ pass`。纯 Python 单测覆盖不到。

### 5.14 测量工具的方差可以完全淹没被测对象的差异（2026-08-10）

本轮做模型消融，五轮跑出**五套互相矛盾的排名**，每一轮的变化都来自我修掉的一个
harness 缺陷，而非模型：

| 轮次 | 脚手架 | GLM-5.2 通过率 | 修掉的缺陷 |
|---|---|---:|---|
| 1 | 单轮 JSON | 25.8% | — |
| 2 | 单轮 JSON | 48.4% | `content or reasoning_content` 跨语义边界 |
| 3 | 单轮 JSON | 67.7%（见下） | 固定 8192 输出预算 |
| 4 | 工具循环 | 83.9% | 换掉整个协议 |

**同一模型、同一批用例，四轮跨度 58 个百分点。** 而模型之间的真实差距只有个位数。

> **不要把这 58pp 读成「仅修 harness」。** 上表第 4 行自己写着「换掉整个协议」：
> 前三轮是 `openai_compat`，第四轮才是 `tool_loop`。`runs/` 下**没有**修复前的 `tool_loop`
> 测量，所以适配器修复与协议变更这两件事在这批数据里分不开。能说的是「仪器变动的量级压过模型
> 差异」，不能说「其中多少来自修 bug」。

> **第 3 轮那格的口径（2026-08-17 补）。** 它对应的 run 目录里 `success_rate` 是 **70.0%**；
> 67.7% 是把同一轮的分子除以 31（集合全量）算出来的，而 `success_rate` 的分母是
> `effective_case_count`（剔除 infra 失败后的 30）。两个数都对，是两个分母。
> 上表其余各格取的是 `success_rate`，所以这一格与它们**不同口径** ——
> 引用时请直接引 `success_rate`，或写明分母。58pp 的跨度用哪一个都成立。

三个缺陷两个同时存在于 `tool_loop` —— **所有校准面板的最强锚点** ——
所以此前发布的每一份难度校准都建立在一个系统性惩罚推理模型的测量上。

判据三条：

1. **看到排名，先看失败原因构成。** 单轮消融的排名 100% 由 JSON 解析失败决定：
   GLM-5.2 的 23 次失败里 22 次是解析报错，只有 1 次是真做了没通过测试。
2. **任何"回退"不得跨越语义边界。** `content or reasoning_content` 在网关把答案放推理字段时
   是对的，在**响应被截断**时是错的 —— 它把「模型没答完」变造成「模型答得不合法」。
3. **测量工具本身要先被测量。** 加一个「无脚手架」的对照口径（`bare_model`），
   它与带脚手架口径的差，就是脚手架贡献的量。实测这个差是 12.9pp 对 0.0pp。

### 5.15 单次运行不能支撑任何排名（2026-08-10）

同一对比、同一批用例：

| | 不一致对 | p 值 | 结论 |
|---|---|---:|---|
| 单次运行 | 6 : 0 | **0.0312** | 「显著」 |
| 三次重复 | 13 : 6 | **0.167** | 不显著 |

`p = 0.0312` 是 6 个不一致对全部同向时**能达到的最小值** —— 结论踩在可能范围内最薄的边上。

更直接的证据：同一模型、同一用例，工具循环下三轮结果翻转率 **25.8%–32.3%**，
而三轮都能稳定分开两个模型的用例是 **0 条**。表面差异全部来自自己就在翻转的用例。

`temperature: 0` 已设置 —— 抖动来自脚手架的路径依赖，换 `bare_model` 后
GLM-5.1 的翻转率降到 **0.0%**（三轮 31 条逐条一致）。

**要求：任何模型比较至少 3 次重复并报轮间极差。**

### 5.16 用流水线自己的语义算，别自己从原始文件统计（2026-08-10）

我从 `result.json` 直接统计锚点通过率，把 `infra_error` 当成用例失败，报出 mid 锚点
19.4%，并据此说「harness 没过滤网关错误」。

**两处都错**：`calibrate.py:278` 本来就跳过 `infra_error`，`calibration.json` 也逐条记录
`attempts`。按正确口径重算是 66.7%。真正的问题是**过滤之后只剩 27/93 有效样本**，
即样本损耗，而非污染 —— 对策是提高 `AIBENCH_CASE_RETRY`，不是「过滤得更狠」。

判据：**流水线有自己的口径时，用它；自己重算等于新写一份实现，而它没被测试覆盖。**

## 6. 当前状态与未尽事项

### 6.1 最大瓶颈：送分题 —— 但归因在 2026-08-05 被推翻

> **本节原结论已作废。** 原文说「任务本身就简单，需要改生成策略：复用真实文件内容 / 反向构造」。
> 2026-08-05 的复算表明这条因果链在本仓库数据上不成立。原文保留在 git 历史里。

**先更正分母。** 上面的 63/24/13 里混了 21 条**没有参考解**的坏题，它们 mean p_hat = 0.008、
**全部** 落在 <0.2 桶。按生成器实际能产出的口径（有参考解，n=105）重算：

| p_hat | 占比 |
|---|---:|
| <0.2 | 8.6% |
| 0.2–0.8 | 16.2% |
| >0.8 | **75.2%** |

送分题问题比原文写的**更严重**；「无人能解」那一侧其实已经基本解决。

**三路独立证据表明「做大做真 ⇒ 更难」不成立**（均在本仓库数据上复算）：

| 证据 | 数值 |
|---|---|
| `corr(impl LOC, p_hat)` | **+0.072**（近 0，且方向相反） |
| `corr(file count, p_hat)` | **+0.121** |
| 按 implLOC 分桶的 p_hat | 0.846 / 0.796 / 0.847 / 0.759 / 0.833 —— 完全平坦 |
| 合成（在宿主周围堆真实文件）配对效应 | **Δ = −0.009**（同面板，n=27） |

**真正的机制：在本语料里「可验证」与「难」是同一个变量。**

| 分组 | n | mean p_hat | >0.8 | ctx LOC 中位数 |
|---|---:|---:|---:|---:|
| 全量 | 126 | 0.677 | 62.7% | 33 |
| 审计通过 | 98 | **0.849** | **78.6%** | 28 |
| 审计失败 | 28 | **0.077** | 7.1% | **388** |

大而真实的用例早就被造出来了 —— 它们无人能解不是因为难，而是**参考解跑不起来**，
门禁正确地删掉了它们，于是剩下的必然是小题。
→ 不先解决可验证性，接地只会把用例从「小而保留」挪到「大而被丢」。

**另外两个常被引用但不成立的数字**：
- 「kata 效应」是「题面点名了被修函数」的混淆变量 —— kata 且题面不点名的用例**有 0 条**。
- 「修复 <15% 行 / LOC<80」那两行 3–8pp 的差距，在有参考解口径下同样不构成杠杆。

### 6.2 T5 产出为 0 —— 阻塞点认错了

原文说卡在 `min_solution_files=2`。实测 `settle_tier` 对 126 条用例的 T5 拒绝原因：

| 原因 | n |
|---|---:|
| `too_few_solution_files` | 126 (100%) |
| `too_few_files` | 120 (95.2%) |
| `too_few_distractors` | 84 (66.7%) |

T5 spec 是 `min_files=5, min_distractors=1, min_solution_files=2`。一个 2 文件的反向构造用例
实测落在 **T3**，`min_solution_files` 根本轮不到生效。**补 T5 需要的是完整物料清单**
（≥2 改动文件 + ≥3 上下文文件含 ≥1 干扰 + ≥4 隐藏测试 + protected_paths），不是放宽一个计数。

**且目前没有任何锚点面板能校准 T5**：`anchor-panel.yaml` 的 weak/mid 缺 A2+A3，
`anchor-panel-retrieval.yaml` 的 weak/mid 缺 A3（`tool_loop_frugal` 无 bash）。
`calibrate_case_set` 对任一不适配成员直接 ValueError，且 `tiers_present` 取自集合内全部用例 ——
**一条 T5 用例就会让整次校准跑不起来**。补 T5 前必须先有一个 A3 可用的弱锚点。

### 6.3 「合成是否让用例更难」—— 已有答案：不会

用同一面板（`weak-frugal-loop` + `mid-frugal-loop`）、27 条配对宿主实测：

| | mean p_hat | >0.8 |
|---|---:|---:|
| `disc-v0` 宿主 | 0.694 | 39.3% |
| `retrieval-v0` 合成 | 0.685 | 37.0% |

**Δ = −0.009 到 −0.028，取决于加权方式；两者都是小幅负值 —— 合成不使用例变难。**

> **更正（2026-08-07）**：此前只报 −0.009。发布校准数据后复算发现那是两个都站得住的算法之一：
> 「池化原始行」给 −0.009，「按锚点等权」给 −0.028。差异来源是 429 限流造成的数据缺损 ——
> 27 条宿主用例里 **6 条只剩 1 次有效尝试**。尝试次数不齐时两种口径必然不同。
> 结论不变，但**我们把两个可辩护数值中的一个当成了「那个数值」**。
> 两种口径都可用 `benchmarks/ai_coding/calibrations/` 里的数据自行复算。

限定：`strong-full-loop` 两轮从未完成（进程被杀），故结论**只对 weak/mid 档成立**；
n=27 远低于 §6.5 所需的 153，属**欠功效**。
数据在 `runs/calibration_20260805_150140/`（宿主侧，4/6 轮）与
`runs/calibration_20260805_144214/`（合成侧）—— **这两个目录不要删**，是唯一的适配面板配对证据。

⚠️ 曾经写进交接稿的「合成集送分率 66.7% vs 基线 63%」是**被污染的对比**
（筛后 27 条 + 检索面板 vs 未筛 126 条 + 单轮面板），同时犯了 §5.2 的错误 #1 与 #3，已作废。

## 7. 下一步建议（按证据排序，2026-08-07 重排）

> 当前分支的完整计划与证据在 `.agent/` 下各任务目录的 `plan.md`。

### 已完成（本轮）

**测量能力**（四阶段，各经 2–3 轮独立评审关闭）：
`collection_error` 把「工作区跑不起来」与「任务难」分开；内容寻址指纹堵住静默复用旧 p_hat；
消毒改为 parse 兜底，不再造出语法错误的参考解；题面点名被修函数的检测与重写。

**组集能力**：`select-cases --difficulty-quota` 按实测 p_hat 难度带配额组集，
欠填如实报告、绝不从相邻带补齐。

**产线加固**：`--max-cases × --oversample` 真正约束成本；case_id 重名不再静默覆盖。

### 待做（按证据排序，2026-08-07 校准后重排）

1. **依赖闭包 —— 唯一还没被打开的门。** §6.1 记的那 28 条：中位 **388 LOC**、
   mean p_hat **0.077**，是这套语料里仅有的「大而真实」样本。它们无人能解**不是因为难，
   是因为参考解跑不起来**（真实 .py 只有 29.8% 没有未解析 import，grader 命令没有安装步骤）。
   P1 已经能把「跑不起来」与「难」分开，但**没有人去修那些工作区**。
   这是目前唯一一批「难度未知、且有理由认为可能真难」的用例。
   做法：给接地工作区做依赖闭包（vendor/stub import，或限定 import-clean 的编辑并如实报丢弃量），
   然后校准它们 —— 这才是第一次真正测量「真实代码任务到底难不难」。

2. **提高每条用例的尝试次数。** p_hat 只能取 `k/(锚点×重复)`。3×2=6 时，
   `SelectionPolicy` 丢掉 0 和 1 之后 **hard 带只剩 1/6 一个值、easy 带只剩 5/6 一个值**。
   15:70:15 这类分布**不是靠多攒用例能达成的**，得先提高分辨率，代价是校准成本线性放大。

3. **消融证明区分度。** 机制已具备（McNemar 配对、按 tier 分层、token 放大倍数）。
   约束：两臂必须同集同面板只变一条轴；§6.5 要求 153 条，不够就如实标注欠功效。

4. **Docker 隔离。** 安全关键，独立基建工程。一旦引入真实仓库代码，这是首要风险。

### 明确不做（均已由实验排除，勿重开）

- **不再试图靠「把用例做大做真」提难度** —— corr `+0.07`（方向相反）、合成 Δ `−0.009`、
  大用例全部挂在可解性门禁。见 §6.1。
- **不再在题面上找难度杠杆** —— 点名率压掉 12.8pp（p=3.1e-09），**难度不动**，
  组内 delta 从 +0.201 掉到 +0.081。见 §4.5、§5.12。
- **不放宽 `p_min` 去凑难题配额** —— 那是把坏题当难题，§5.3 记过这个坑。

> 这两条都走完了「建集 → 校准 → 复算」的完整循环才被排除。
> 重开它们之前，请先读 §5.12：观察数据上的相关性（哪怕 p<1e-8）不构成证据。

```bash
  --output-dir benchmarks/ai_coding/cases/_cases --reverse \
  --max-cases 120 --oversample 30 --workers 5 --resume --audit --secrets-scan

  --case-set _revmixed --parallel 3
```
