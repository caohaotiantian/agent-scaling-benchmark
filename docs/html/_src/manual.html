2. 端到端流程

1抽取草稿

uv run aibench extract-from-db \
  --output-dir benchmarks/ai_coding/cases/_drafts \
  --limit 30000 --max-cases 12000 \
  --require-edits --all-agents \
  --min-messages 3 --max-messages 400

不消耗模型额度，只读数据库。草稿逐条落盘，中途中断已产出部分仍保留。

--require-edits
只取真正修改过代码的会话。反向构造需要编辑前后两个版本，按时间抽样几乎取不到：150 条近期记录只产出 1 条可用，加此参数后为 21 条。
--max-messages
影响最大的参数。 默认 60 会丢弃 69% 的含编辑会话，且丢弃的正是编辑最多的长会话。放宽到 400 后语料从 1,229 条增至 4,687 条。
--all-agents
不限定来源客户端。不加此参数会额外过滤掉约 15% 的记录。
--limit
数据库扫描行数上限。
--max-cases
写出草稿数上限。

2生成用例

uv run aibench generate-cases \
  --input-dir benchmarks/ai_coding/cases/_drafts \
  --output-dir benchmarks/ai_coding/cases/_cases \
  --reverse --max-cases 120 --oversample 30 \
  --workers 5 --resume --audit --secrets-scan

消耗模型额度。 每条可用草稿一次调用。

--reverse
启用反向构造：stub 取编辑前版本，参考解取编辑后版本，模型只写测试与题面。不加则退回「让模型编题」的旧路径。
--oversample
为写出 N 条用例而尝试的草稿倍数。直接决定费用：--max-cases 120 --oversample 30 意味着最多扫描 3,600 条草稿。反向模式下无可用编辑对的草稿在调用模型之前即被剔除，不计费。
--workers
并发数。实测 5 较稳妥；8 会触发网关限流。
--resume
续跑未完成的任务。已写出的用例与已判定的草稿不再送模型。建议始终开启。
--audit
生成后立即运行效度门禁并写回结果。
--secrets-scan
扫描密钥并输出报告。

中断安全。 用例一产出即落盘，同时向输出目录的 _progress.jsonl 追加一行。进程被杀后，用 --resume 重跑只会补做未完成的部分。实测一次被限流中断的运行：3,166 条已判定草稿全部跳过、零重复计费，仅重试 146 条。

3效度审计

uv run aibench audit-cases --case-set _cases --annotate

不消耗额度，在本地实际运行每条用例的测试。输出形如：

audit case_set=_cases passed=43/120 failed=77 uncollectable_stub=54 \
      uncollectable_reference=44 fingerprint=…
--annotate
把审计结论写回用例的 metadata.validity_ok，供后续步骤筛选。
--fail-on-error
存在错误级问题时以状态码 2 退出，便于接入 CI。

通过率约 36%–45% 属正常。主要失败原因为 uncollectable——真实文件依赖单文件工作区无法提供的模块。

4难度校准

uv run aibench calibrate-cases --case-set _cases \
  --anchors configs/runs/anchor-panel.yaml \
  --repeats 3 --parallel 3 --workers 3

消耗额度，耗时最长。 总运行次数 = 用例数 × 锚点数 × repeats。31 条用例约需 2–3 小时。

--repeats
每个锚点独立运行次数。决定 p_hat 的分辨率，见下表。
--parallel
并发的锚点通道数。
--workers
每个通道内并发的用例数。对网关的总压力约为二者之积，实测余量约 16。
--reuse-from
指定既往校准结果；内容与面板均未变的用例直接复用，不重跑。
repeats每条尝试次数难档可取值易档可取值
260, 0.1670.833, 1.000
390, 0.1110.889, 1.000

p_hat 是量化值，只能取 k /（锚点数 × repeats）。跨不同 repeats 比较档位占比时必须声明——分辨率变化本身就会移动占比，不可将其算作难度变化。

5挑选可用集合

uv run aibench select-cases --calibration runs/calibration_…/calibration.json \
  --output-set my-benchmark

依据校准结果保留有区分度的用例。判定条件：通过率处于中段、且强弱锚点之间存在可测量的差距。

6度量与消融

# 单次评测
uv run aibench run --case-set my-benchmark \
  --agent configs/agents/tool_loop.yaml \
  --model configs/models/glm52.yaml \
  --run-config configs/runs/baseline-tool-loop.yaml

# 消融矩阵
uv run aibench ablation --matrix configs/runs/ablation-matrix.yaml \
  --case-set my-benchmark --parallel 3

消融会按矩阵逐一改变单个变量并比较结果差异。所需样本量可用 plan-sample-size 估算。

3. 三种测量口径：先想清楚在测什么

项目提供三个 agent 适配器。它们回答的不是同一个问题，混用是此前五轮矛盾结论的根源。

适配器回答的问题协议何时用
bare_model模型本身有多强一次调用，回一段围栏代码比较模型
openai_compat模型 + 单轮 JSON 协议整个文件塞进 JSON能力下限锚点
tool_loop模型 + 多步工具循环可读写文件、跑测试、迭代能力上限锚点

实测证据（同一批 31 条用例、同两个模型、各 3 次重复）：

口径GLM-5.1 轮间极差Deepseek 轮间极差GLM-5.1 逐用例翻转率胜者
bare_model0.0pp3.2pp0.0%GLM-5.1 (90.3%)
tool_loop12.9pp16.1pp32.3%Deepseek (90.3%)

脚手架贡献了几乎全部测量噪声，并且颠倒了排序。 比较模型时使用 bare_model； 用带脚手架的口径得到的排名，测的是「模型 + 该脚手架」的组合。

任何模型比较至少 3 次重复并报轮间极差。 同一对比单次运行给出 p = 0.0312「显著」， 三次重复给出 p = 0.167 不显著 —— 单次运行不足以支撑排名。

uv run aibench ablation --matrix configs/runs/ablation-bare-models.yaml \
  --case-set _revmixed --parallel 3

该矩阵已内置 3 次重复。要换模型，复制它并替换 model_config 指向的文件。

4. 调整难度分布

若产出的用例过于集中在易档，可用隐藏测试提高难度。该机制把模型写的测试拆成可见与隐藏两部分，隐藏部分仅在评分时注入。

隐藏条数最强锚点通过率效果说明
0（全部可见）90.3%Agent 可反复运行测试直至全绿
187.5%几乎无影响
250.0%通过率腰斩
346.7%—
433.3%—
5 及以上0%过度隐藏，退化为无人能解
 
# 只对易档用例隐藏 2 条测试（当前最优配置）
uv run python -c "
import json; from pathlib import Path
from aibench.extract.tier_shaping import split_tests_for_hiding
cal = {c['case_id']: c['p_hat'] for c in json.load(open('runs/calibration_.../calibration.json'))['cases']}
for p in Path('benchmarks/ai_coding/cases/my-set').glob('*.json'):
    c = json.loads(p.read_text())
    if cal.get(c['case_id'], 0) > 0.8:          # 仅易档
        split_tests_for_hiding(c, hide_count=2)
        p.write_text(json.dumps(c, indent=1, ensure_ascii=False))
"

务必按「隐藏条数」控制（hide_count），而非「保留条数」（keep_visible）。 模型通常写 4–10 条测试，「保留 3 条」与「保留 1 条」实际隐藏中位数分别为 2 条与 4 条，都已越过崩塌点，实测结果几乎相同。

过度隐藏会把「仅最强能解」变成「无人能解」，而后者与送分题一样不产生区分度：实测区分度用例由 26 条降至 11 条。

5. 用例在哪里：可复用的产物清单

用例本身不入库。 反向构造的用例逐字包含真实仓库源码（实测 13%–75.2%）， 因此 benchmarks/ai_coding/cases/_rev*/ 全部在 .gitignore 中。 克隆本仓库不会得到用例文件，只会得到生成它们的代码与校准数字。

产物位置是否入库说明
_revmixedbenchmarks/ai_coding/cases/_revmixed/否当前最优集合：31 条，全部通过效度门禁，易档已按 hide_count=2 处理
_revfinal2同上目录否同 31 条，测试全部可见（未做隐藏处理）
_rev6同上目录否120 条原始产物，其中 43 条通过门禁
_rev_raw4同上目录否3,312 条草稿，重跑生成的输入
校准数据benchmarks/ai_coding/calibrations/是14 份，纯数字无代码，任何人可复算
运行记录runs/否含 grade.detail，可能带测试源码

取用方式

要把用例交给他人，走导出流程而非直接复制目录 —— 导出会逐条过五道门禁，并生成说明清单：

uv run aibench export-bundle --from-set _revmixed \
  --output-dir /要交付的路径 \
  --drafts-dir benchmarks/ai_coding/cases/_rev_raw4 \
  --allow-production-derived

产出目录含通过门禁的用例与 MANIFEST.json，后者逐条记录源文件名、语言与实测逐字比例。 不加 --allow-production-derived 时反向构造用例会被全部拒绝，理由 production_derived。

6. 对外分发的门禁

uv run aibench export-bundle --from-set my-benchmark \
  --output-dir /path/outside/repo \
  --drafts-dir benchmarks/ai_coding/cases/_drafts

导出前逐条检查五道门禁，任一不过即排除并在清单中记录原因：

门禁判定是否可绕过
schema符合用例 JSON 结构否
auditvalidity_ok 为真--no-require-audit
secrets密钥扫描为空否
provenance非启发式回退产物否（该路径逐字复制草稿，即生产代码）
verbatim与草稿逐字重合比例低于阈值--max-verbatim

反向构造的用例默认被拒绝，理由是 production_derived。 这类用例按定义逐字包含真实仓库源码，实测逐字比例 13%–75.2%。

确需分发时使用 --allow-production-derived。该开关不跳过任何检查，其余门禁照常生效；它记录「分发生产代码是有意为之」这一决定，并在清单中逐条写明源文件名、语言与实测逐字比例，使接收方知悉所收内容。

7. 复现已发布的结论

已发布的校准结果为纯数字，不含任何代码，位于 benchmarks/ai_coding/calibrations/。任何一项报告数值都可独立复算：

import json, collections, statistics

def band(p):
    return 'hard' if p < 0.2 else ('mid' if p <= 0.8 else 'easy')

j = json.load(open('benchmarks/ai_coding/calibrations/reverse-v1_3anchor_20260808.json'))
v = [c['p_hat'] for c in j['cases']]
print(collections.Counter(band(x) for x in v), statistics.mean(v))
已报告数值复算方法
reverse-v1 易/中/难 = 22.6 / 74.2 / 3.2使用 reverse-v1_3anchor_20260808.json 全部 31 条
auto-v0 易/中/难 = 75.2 / 16.2 / 8.6使用 auto-v0_3anchor，仅取有参考解的 105 条
隐藏测试剂量曲线对比 reverse-v1 与 reverse-v1-keep3、reverse-v1-hidden1

比较前先确认面板一致。 anchor_fingerprint 哈希的是锚点配置文件的内容而非路径。指纹不同不必然意味着行为不同——例如某次提交仅为配置增加了声明性字段，不改变 Agent 行为。既不要因指纹相同就假定可比，也不要因不同就放弃比较。

8. 故障排查

现象原因处理
HTTP 429，消息含 budget_exceeded凭据额度耗尽，与并发无关提额或更换凭据。程序会立即失败，不再重试
HTTP 429，消息含 rate limit并发过高降低 --workers，程序会退避重试
HTTP 403，提示模型不在允许列表凭据未授权该模型报错信息会列出允许的模型名
大量 timed out源文件过大，单次生成耗时长属瞬时失败，不记账；--resume 会重试
审计报 uncollectable 比例高真实文件依赖工作区不存在的模块正常现象，这些用例应被剔除
输出目录长时间为空抽取与校准在结束时才汇总输出观察 _progress.jsonl 行数或运行目录下的 result.json 数量

判断长任务是否存活：用一次独立的 pgrep 确认进程存在，不要以「已发出启动命令」为依据。若使用轮询等待，模式串不可出现在发起它的那条命令中，否则会匹配到等待进程自身，导致永远等待。
