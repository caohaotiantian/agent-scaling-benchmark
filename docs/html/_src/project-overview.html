一、项目目标与边界

在统一 Benchmark 协议下，比较不同 Agent / 模型配置在 AI 辅助编程 任务上的质量、Token 与耗时，服务 Agentic Scaling 横向对比与汇报。

做的事

MySQL llm_chat_records 抽库 → 规则筛选 → LLM/启发式生成可机评 case → 替换 Agent/模型跑测 → 写出 summary / tables / 消融报告。

不做的事

自动无人审核发布正式集；Fusion/投机算法本体；完整 IDE UI 仿真； 不设上限的全库无限扫描；编造无数据源的结果列。

生产默认： Agent = openai_compat，模型 = GLM-5.2（OpenAI 兼容 API）， case 集 = auto-v0，消融矩阵对比 openai_compat vs tool_loop。 Mock 仅存在于 tests/fixtures 与 --dry-run。

二、核心概念

术语定义
Case一条可评测任务：prompt + workspace + grader
Case set一组 case 的目录名，如 auto-v0（候选）、prod-v0（发布）
Draft从会话抽出的草稿，未必可跑
Run一次完整实验：固定 case 集 + 一种 Agent/模型/算法配置 + 预算
消融 Ablation同一 case 集上跑多组配置并横向对比（对照实验矩阵）
主指标task_success_rate = 成功数 / 有效 case 数（排除 infra_error）
有效 case非基础设施错误、可计入成功率的 case
weak_grader判分偏弱标记；消融默认剔除

三、系统架构与数据流

数据层 MySQL llm_chat_records / JSON sessions 导出 │ ▼ 构建层 extract-from-db → filter-drafts → generate-cases (+ audit-cases / secrets-scan) │ ▼ Case 集 benchmarks/ai_coding/cases/auto-v0/ │ ▼ 执行层 materialize workspace → Agent.run → grade (case_workers 并行 · HTTP/infra 重试) │ ▼ 报告层 summary.json · tables.json · report.md ablation_report.md（多配置对比）+ CSV/XLSX

分层职责

构建层

src/aibench/extract/：抽库、筛选、生成、软过滤、snapshot 骨架。

执行层

runner + agents/* + grading + workspace。

报告层

report / ablation / stats（Wilson CI、分层）。

仅生成用例时： 做到 generate-cases + validate/audit 即可停止。 完整 e2e_pipeline.sh 末尾会自动执行 消融。

四、「消融」在本项目中的含义

这里的消融 = 对照实验：固定测评集，只改 Agent/模型（及算法标签）， 比较成功率、Token、耗时、相对基线收益。 与「删掉网络层做学术消融」不是同一操作，而是配置矩阵上的系统对比。

与设计一致： 「一行结果 = 同一 Benchmark + 同一 case set + 一个算法配置 + 预算档 + 一次 run」。 见 agentic-scaling-benchmark.html。

生产矩阵 configs/runs/ablation-matrix.yaml 默认对比：

  • 基线 openai_compat + GLM-5.2（实验名 openai-compat-glm52）
  • 对照 tool_loop + GLM-5.2

5.5 --limit 与 --max-cases

参数 CLI 默认 e2e 脚本默认 含义
--limit 300（抽库） 100 DB 最多扫描多少行
--max-cases（抽库） 30 max-cases × 3 最多写多少草稿
--max-cases（生成） 50 8 最多写多少最终 case

不传参则用默认，不会全库无限扫描。limit = 读库预算；max-cases = 写出预算。

5.6 推荐工作流（步骤）

  1. 环境 — uv sync，配置 .env（DB + OPENAI_*）
  2. 构建候选集 — extract → filter → generate → validate/audit → 得到 auto-v0
  3. 单次基线 — run_benchmark.sh 或 aibench run
  4. 消融对比 — 改矩阵中的 Agent/模型行，读 ablation_report.md
  5. 人工发布 — promote --require-audit 到 prod-v0

八、Case 协议与科学效度

必填

grader.mode

gold 文件/key_lines 匹配

8.1 「科学效度」指什么？

这里的科学效度（scientific validity）不是统计学术语里完整的「构念效度」检验， 而是评测工程上的一组可自动执行的质量门禁：确保 case 适合作为公平、可区分、可复现的基准题， 避免「题面已含答案」「初始代码已能过测」「题目过短/重复」等使成功率失真的情况。

目标：测到的差异应尽量来自 Agent/模型能力，而不是题目泄漏、空题、或基础设施噪声。 实现模块：src/aibench/validity.py，命令：aibench audit-cases。

8.2 有哪些门禁？严重级别？

门禁 代码 / 检查名 级别 失败时 ok? 含义（一句话）
Stub 必须失败 stub_fail_gate error 否 初始 workspace 上跑 grader 必须不过，否则题无区分度
答案污染 · gold contamination_gold_in_context error 否 gold 全文（≥40 字符）已出现在 context 文件中 → 泄漏
答案污染 · key_line contamination_keyline_in_context error 否 gold 模式且关键行（≥8 字符）已在 context 中 → 可平凡通过
Prompt 过短 prompt_too_short error 否 prompt 去空白后 < 20 字符
Prompt 大代码块 prompt_contains_large_code_fence warn 是（仅警告） prompt 含很大 ``` 代码块且含 “implement” → 疑似泄漏，人工复核
弱 grader 标记 weak_grader_flag warn 是 script 模式却标 weak_grader=true，配置可疑
重复指纹 duplicate_fingerprint warn 是 同集内 task_type+prompt+路径指纹相同 → 疑似重复题
难度估计 difficulty 注解 — 启发式 easy/medium/hard，用于分层报告，不单独 fail
指纹 / 集指纹 fingerprint / content_fingerprint 注解 — 单 case 去重信号；整集内容指纹写入 run manifest 便于复现

CaseValidityReport.ok = 无任何 error 级 issue。 warn 不阻断 ok，但会写入 issues。

8.3 各门禁逻辑（算法细节）

① Stub-fail（script 题核心门禁）

若 grader.mode != script 或无 command： → 跳过，记 detail=skipped_non_script，视为通过 否则： 1. 临时目录 materialize_workspace(case) # 初始现场，不经 Agent 2. grade_case(case, workspace) # 跑 pytest/python 等 3. 若 infra_error → 门禁失败（环境/命令问题） 4. 若 grade.passed == True → 门禁失败（stub_passed_grader） # 初始代码已能过测 → 题目无意义 5. 若 grade.passed == False → 门禁通过（stub_failed_as_expected）

意图：Agent 必须做出有效修改才能得分；否则成功率虚高。

② Contamination（污染 / 答案泄漏）

blob = 拼接全部 context.files 的 path+content 对每个 gold_file： 若 content 去空白后长度 ≥ 40 且 content ⊆ blob → error: contamination_gold_in_context 对每个 key_line（仅当 grader.mode == gold）： 若 strip 后长度 ≥ 8 且 key_line ⊆ blob → error: contamination_keyline_in_context 若 prompt 匹配「大代码围栏 + implement」： → warn: prompt_contains_large_code_fence

意图：防止「题面/初始文件已含标准答案」，模型只需复制即可满分。

③ Prompt 长度

len(prompt.strip()) < 20 → error: prompt_too_short。过滤空题、噪声片段。

④ 难度（启发式，不 fail）

score = 文件数 + test_ 函数数 + 总行数//40 score ≤ 4 → easy score ≤ 12 → medium else → hard

用于 summary 分层成功率，不是绝对难度标定。

⑤ 指纹与去重

case_fingerprint = sha256(task_type | prompt | sorted(paths))[:16] set content_fingerprint = sha256(排序后的 "case_id:fp" 列表)[:16] 同集内相同 fingerprint 的多条 case： → 各自追加 warn: duplicate_fingerprint

⑥ 与发布门控 promote 的关系

audit-cases 只管效度报告；正式发布另有 promote 门控（可叠加）：

  • Schema 合法
  • 默认要求 grader.mode=script（可用 --allow-non-script 放宽）
  • 拒绝 weak_grader=true
  • 默认 secrets-scan 干净（可用 --allow-secrets 放宽）
  • --require-audit 时再要求 audit_case.ok == true

8.4 报告侧相关（非 case 门禁，但同属「可科学解读」）

  • Wilson 95% CI：小样本成功率置信区间，避免单点比例误读
  • 有效 case：排除 infra_error 后计成功率
  • 分层：按 task_type / difficulty 分层成功率
uv run python -m aibench audit-cases --case-set auto-v0 \
  --annotate --report /tmp/audit.json --fail-on-error

uv run python -m aibench promote --from-set auto-v0 --to-set prod-v0 \
  --require-audit --case-id my_case

十、与初始设计文件的关系

agentic-scaling-benchmark.html

结果表设计报告：统一数据粒度、综述表、通用总表、确定性/偏好型任务、 推荐落盘结构、落地阶段。定义「表应该长什么样、一行代表什么」。

tables.html

字段字典：综述表与通用总表每一列的含义与建议类型。 实现填表时的列名与语义权威来源。

本仓库实现 = 按上述合同跑实验并落盘填数： tables.json.overview_row ↔ 项目效果综述表； summary.json / general_row ↔ 通用结果总表核心字段； 主指标名显式为 task_success_rate（半确定性 AI 编程任务）。 无数据的列保持 null，不编造。
设计要求实现映射
一行 = Benchmark + case set + 算法配置 + 预算 + run 一次 aibench run 或消融矩阵中的一行
综述表（轻量汇报） overview_row / ablation_report.md
通用总表细分列 summary.json 键 + general_row
落盘 runs/… runner 写出的标准目录
