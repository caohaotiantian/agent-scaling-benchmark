1. 方案设计依据

1.1 为什么用「相对锚点的通过率」度量难度

难度不能靠人工标注，原因有二：标注不可复现；标注反映的是标注者的判断，而非被测 Agent 的实际表现。

本项目将难度定义为一组固定参照配置的通过率。这带来三个性质：

  • 可复现——只要面板配置不变，任何人重跑都能得到同一分布。
  • 可比较——两批用例只要用同一面板测量，结果可以直接对照。
  • 有边界——测得的是「相对这组参照配置的难度」，面板变了含义就变了，因此面板身份必须随结果一同发布。

1.2 锚点面板的构成原则

面板必须跨越待区分的能力范围。三个近似的配置会把所有用例都判为无区分度。

锚点脚手架模型隔离的变量
weak-single-turn单轮，无工具较弱能力下限
mid-single-turn单轮，无工具较强与上一行对比 ⇒ 模型维度
strong-tool-loop多步工具循环较强与上一行对比 ⇒ 脚手架维度

面板配置文件格式：

anchors:
  - name: weak-single-turn
    agent_config: configs/agents/openai_compat.yaml
    model_config: configs/models/glm51.yaml
    run_config:   configs/runs/baseline.yaml
  - name: strong-tool-loop
    agent_config: configs/agents/tool_loop.yaml
    model_config: configs/models/glm52.yaml
    run_config:   configs/runs/baseline-tool-loop.yaml

1.3 严格顺序重放

从会话还原文件的编辑前后版本时，只在「会话确实读取过的内容」上应用编辑。

匹配策略重建率风险
严格顺序（本项目采用）较低无
在任意历史快照中搜索较高可能匹配到错误版本，重建出从未存在过的中间状态

用一个从未存在过的状态构造的用例，是「带着真实代码的虚构」。本项目宁可损失产量。

3. 效度门禁

「跑不起来」的判定依据

判定取自运行器自己报告的用例计数，而非在输出文本中匹配错误特征。文本匹配在两个方向上都会出错：

  • pytest 把测试固件的导入失败记为「1 error」、退出码 1，且不打印收集失败横幅——只认横幅的匹配器会漏判。
  • 一条断言内容涉及 SyntaxError 或 ERR_MODULE_NOT_FOUND 的正常测试，会把匹配器要找的所有特征放进普通的断言差异里——从而误判。

因此：只要运行器报告了任何通过或失败计数，就说明它到达了判定；一个计数都没有，则覆盖了未解析的导入、语法错误、启动失败与中断等全部情形。

补充规则

规则依据
待修复版本「跑不起来」时，若其为完整文件（反向构造），直接拒绝反向构造的 stub 是真实可运行文件，不存在「函数尚未实现」这一合理解释。实测 6 条通过门禁的用例中有 5 条是因编辑前后导入差异（一版引入 numpy、另一版未引入）而「区分成功」，与缺陷无关
无参考解的用例一律拒绝实测 18 条无配置可解的用例中，16 条没有参考解
测试文件名必须是运行器真正会发现的名字空跑退出 0 会被读成「stub 通过」
测试不得 grep 实现的源码文本（test_reads_source_text）源码文本天然区分编辑前后两版，这类测试按构造通过上面两道门禁，而它评的是抄写不是行为。实测 31 条中 12 条如此
只改注释的编辑不作为缺陷（defect_is_not_semantic）剥离注释与 docstring 后两版相同即拒绝。曾有两条用例的实现与参考解逐字节相同、通过率 1.00 与 0.00，「缺陷」是一次注释清理
测试文件本身不作为被测实现会生成「给测试写测试」的用例。草稿池中 27/91 的 Python 编辑对落在此类

测试抄写源码：反向构造安全性论证的漏洞

反向构造的立论是：模型写不出能区分编辑前后两版的测试，用例就会被上面两道门禁拒掉， 所以模型没有能力把题变简单。这个论证有一个洞——源码文本天然能区分两版， 因为修复改动的就是文本。一份 assert.match(source, /async function prepareReview/) 这样的测试在待修复版本上必失败、在参考解上必通过，两道门禁按构造 100% 通过。

实测当前集合 31 条中 12 条如此，语种分布 JavaScript 11/14、Python 1/17。

判定规则（三条并集）命中独有命中
反射取源码（inspect.getsource / getsourcelines）11
含读调用的那一行里出现实现文件名（排除写模式）41
存在读调用且有字符串包含/正则断言107
并集12—

第二条只看含读调用的那一行而非整个文件，是刻意的：JavaScript 测试必然在 import 行写出实现文件名， 按全文匹配会退化成「任何读操作都算」，同一集合上从 4 条涨到 11 条，把合法的数据 fixture 读取也抓进来。 单条宽正则还会额外误伤 5 条——4 条用 open(..., 'w') 写 fixture，1 条在测真实 HTTP 端点。 隐藏测试与可见测试一起扫描，抄写可以藏在求解者看不到的那一半里。

4. 校准结果格式

校准输出为 calibration.json，仅含数字与标识，不含任何代码，因此可以公开发布。

{
  "anchors": ["mid-single-turn", "strong-tool-loop", "weak-single-turn"],
  "repeats": 3,
  "anchor_fingerprint": "5f5233c7214879f4",
  "cases": [
    {
      "case_id": "rev-…",
      "p_hat": 0.222,
      "spread": 0.667,
      "point_biserial": 0.830,
      "keep": true,
      "by_anchor": {
        "weak-single-turn": 0.00,
        "mid-single-turn": 0.00,
        "strong-tool-loop": 0.67
      }
    }
  ]
}
字段含义
p_hat全部尝试的通过比例。量化值，只能取 k /（锚点数 × repeats）
spread最强锚点与最弱锚点的通过率之差。衡量区分能力
point_biserial用例结果与锚点强度的点二列相关。越高说明越能按能力排序
keep是否判定为有区分度
by_anchor各锚点各自的通过率，用于诊断
anchor_fingerprint面板身份。哈希的是锚点配置文件的内容而非路径

原始运行结果 results.jsonl 不发布。 其 grade.detail 字段包含运行器回溯信息，实测 59 条失败记录中有 27 条含测试源码。

6. 复现环境说明

评分在本机环境中执行，因此环境差异会影响结果。以下为已知的关键依赖：

项影响
Node 版本< 22 无法执行 TypeScript 测试；语言规格中的发现规则按 Node 24 实测确定
Python 第三方包评分环境未安装 numpy、pandas 等。导入这些包的用例在生成前即被过滤
网络评分工作区禁用网络。测试若发起真实网络请求，用例会被审计拒绝——此类用例本身不可复现

7. 术语表

draft 草稿
从一条会话记录抽取出的中间产物，尚未成为用例
stub
用例中待修复的代码。反向构造中即编辑前的真实文件
gold 参考解
用于验证测试有效性的正确版本。反向构造中即编辑后的真实文件
anchor 锚点
用于度量难度的固定参照配置
p_hat
某用例在全部锚点尝试中的通过比例
spread
最强与最弱锚点通过率之差
uncollectable
测试未能运行（而非运行后失败）
verbatim share
用例中逐字来自源仓库的实质代码行占比
