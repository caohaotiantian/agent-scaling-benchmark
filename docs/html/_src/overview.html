项目介绍

本项目从现网 AI 编程助手的真实会话记录中，生成能够区分不同 Agent 能力的 benchmark 用例，并给出可复现的度量流程。

AI-Coding-Assist Benchmark 数据来源 · 现网 trace 度量 · 三锚点校准

1. 背景

评测一个编程 Agent，需要一批能区分能力差异的题目。如果一批题目所有配置都能做对，或所有配置都做不对，那么无论运行多少次，都无法比较两个配置的强弱。

本项目最初用大模型直接生成用例：把一条真实会话交给模型，让它写出一道编程题。这条路线的产物有一个稳定的问题——题目太简单。在 126 条用例的基线集合 auto-v0 上实测：

为定位原因，项目做了三次独立干预实验，每次都以「干预之后难度是否改变」为判据：

假设实测结果结论
用例做得更大、更贴近真实代码 ⇒ 更难相关系数 +0.07，方向相反否定
题面不点名被修改的函数 ⇒ 更难干预本身成功（p = 3e-09），难度未变否定
源会话越复杂 ⇒ 用例越难全部 |r| ≤ 0.225，不显著否定

三次实验共同指向同一个解释：无论输入什么，生成器都输出同一种难度。60 条校准用例中有 39 条通过率恰好为 1.000。问题不在于参数没调对，而在于「让模型自己编题」这一步本身。

2. 项目目标

  1. 用现网真实数据生成用例，而不是让模型凭空编题。
  2. 用例具备能力区分度：不同强度的 Agent 配置在同一批题上应表现出可测量的差异。
  3. 难度分布接近 15 : 70 : 15（易 : 中 : 难），即中间厚、两端薄。
  4. 可复现：环境就绪的前提下，他人可以重跑全流程并核对我们报告的每一个数字。

3. 项目架构

整条流水线是单向的：真实会话记录 → 草稿 → 用例 → 校准 → 可用集合 → 度量。每一步都有独立的命令与产物，可以单独重跑。

4. 实现原理

4.1 反向构造：缺陷不由模型决定

既然「让模型编题」会把一切输入压成同一种难度，那就不让模型决定缺陷是什么。

一条真实会话里，工程师对文件做过若干次编辑。把这些编辑按时间顺序重放，可以还原出该文件修改前和修改后的两个版本。于是：

重放采用严格顺序匹配：只在会话确实读取过的内容上应用编辑。宽松匹配（在任意历史快照里搜索）能得到更高的重建率，但一次匹配到错误版本，就会重建出一个从未存在过的中间状态，用例便成了「带着真实代码的虚构」。本项目选择前者。

4.2 难度如何度量

难度不是主观标注，而是相对一组固定参照配置的通过率。参照组称为锚点面板，包含三个能力档次：

锚点构成用途
weak-single-turn单轮改写，无工具能力下限。此处也能过的题是送分题
mid-single-turn同一脚手架，更强模型隔离「模型」这一变量
strong-tool-loop多步工具循环，可运行测试并据此修改能力上限。隔离「脚手架」这一变量

每个锚点独立运行 repeats 次，p_hat 是全部尝试的通过比例。注意它是量化的：只能取 k /（锚点数 × repeats）。repeats=3 时每条用例 9 次尝试，难档 p<0.2 只有 0 与 0.111 两个可取值。

5. 关键模块技术细节

A语言规格 languages.py

每种语言登记一份规格：测试文件命名规则、测试声明写法、运行命令、如何从运行输出中读回通过/失败计数。

只登记本机真能执行的语言。 登记一个跑不起来的工具链，会让用例在所有配置上一律失败——那看起来是难题，实际是坏题。

命名规则按运行器实测确定，而非沿用惯例。实测：node --test 不发现 test_app.js（退出 0、零测试运行），pytest 不发现 a.spec.py（退出 5）。空跑退出 0 会被读成「stub 通过」，从而误判用例无效。

B效度门禁 validity.py

三道错误级门禁，任一不过则用例不可用：

stub_fail
测试必须在待修复版本上失败
solvability
测试必须在参考解上通过
collection
失败必须是「测试判定为不通过」，而非「工作区跑不起来」

第三条最关键：缺依赖、语法错、导入失败，都会让所有配置一律失败，与真正的难题不可区分。判定依据取自运行器自己报告的用例计数，而非在输出文本里匹配错误特征。

C导入可满足性过滤

评分工作区只有两个文件：待修复文件与测试文件。真实仓库里的文件常常导入第三方包或同仓库的兄弟模块，两者都不在工作区内。

这类用例在生成之前就被剔除，因为生成是花钱的一步。实测该判据是完美预测器：16 条导入不可满足的用例，16 条全部未通过效度门禁。

D断点续跑 checkpoint.py

用例一产出即落盘，并向 _progress.jsonl 追加一行（逐行 flush）。--resume 读取它，已结案的草稿不再送模型。

确定性拒绝记账（下次判还是同样结果），瞬时失败不记账（超时、限流应当重试）。日志永不压过文件系统：用例被删则不计为已写；被杀时写坏的最后一行跳过，不因一行残缺丢弃整批。

6. 生成用例的分布与样例

6.1 实测难度分布

反向构造集合 reverse-v1，31 条用例、三锚点、repeats=3，共 279 次尝试，其中「工作区跑不起来」仅 1 次。

指标auto-v0reverse-v1
用例数12631
平均通过率 p_hat0.6770.527
判定为有区分度28（22.2%）26（83.9%）
区分度中位数 spread—1.000

与基线的差异检验：假设真实易档比例仍为 auto-v0 的 75.2%，则观察到 31 条中仅 7 条为易档的概率为 1.15e-09。

6.2 按能力档次分类

按 p_hat 分档之外，更贴近使用目的的看法是：哪一档能力能解出这道题。

类别占比对区分度的价值
三档全部解出（送分题）12.9%无
仅最强配置解出45.2%最高
介于两者之间41.9%有
三档均无法解出0%无

关于难档 3.2% 未达标。 p_hat < 0.2 要求 9 次尝试中至多通过 1 次，即最强锚点也几乎全败。实测最强锚点平均通过率 90.3%，且 31 条中有 23 条它是三次全过——这些用例的 p_hat 下限被钉在 1/3，在算术上就不可能进入难档。

已验证：没有任何输入特征能改变这一点（编辑次数 |t|=1.22、改动行数 1.57、文件行数 1.80，均不显著）。真正起作用的是任务形态——见下节。

6.3 隐藏测试：唯一能撼动最强锚点的杠杆

把模型写的测试拆成两半：一部分留在工作区供 Agent 查看和迭代，其余仅在评分时注入。能运行测试的 Agent 便无法靠「反复跑到全绿」收敛。

据此实测四个档位，全部作用于同一批 31 条用例、同一面板：

设置最强锚点难档无人能解有区分度
全部可见90.3%1026
隐藏 2 条55.9%121116
保留 3 条可见52.7%141215
保留 1 条可见47.3%151411
目标—≈5≈0越高越好

该杠杆须按「隐藏条数」控制，而非「保留条数」。 模型通常写 4–10 条测试，因此「保留 3 条」实际隐藏中位数 2 条、「保留 1 条」隐藏中位数 4 条——两者都已越过崩塌点，实测结果几乎相同。

没有一个全局档位能命中目标。 隐藏 1 条几乎不起作用（最强锚点 87.5%），隐藏 2 条已经把 11 条用例推入「无人能解」、区分度由 26 降至 16。可用区间被模型所写的测试条数卡死，粒度不足。

关于推算与实测的差异。 事前用配对数据推算的结果是易档 4 条、区分度 26 条，实测为 5 条与 24 条。差异方向与事前标注的一致：该策略按实测通过率挑选易档，其中一部分是噪声推高的，重测会自然回落。推算可用于预判，不可直接当作结论。

7. 已知边界

  • 样本量：当前 31 条。消融实验若要达到既定检验效能，需要 153 条。当前结论均附 95% 置信区间，应作为方向性结论使用。
  • 语言覆盖：仅支持 Python 与 JavaScript / TypeScript。这是产量的首要上限，作为待决问题单列于第 8 节。
  • 难档：受最强锚点能力封顶。当模型能力提升时，需要相应调整任务形态，否则集合会饱和。
  • 用例含生产代码：反向构造的用例按定义逐字包含真实仓库源码，实测逐字比例 13%–75.2%。对外分发受专门门禁约束，详见用户手册。

8. 待决问题：语言覆盖

本节供内部讨论使用。 陈述问题、实测数据、技术阻塞点与可选方案及其代价，不预设结论。

8.1 问题陈述

当前只有 Python 与 JavaScript / TypeScript 的用例能够生成并评分。真实工程师改动最多的 C++、Rust、C 等语言全部无法进入流水线，这是产量与代表性的双重上限。

8.2 实测数据

8.3 为什么不能直接登记新语言

约束写在语言规格模块的开头：只登记本机真能执行的语言。登记一个未安装的工具链，会让用例被生成、被定级、被发布，直到评分时才失败——而且是在所有配置上一律失败。

「跑不起来」与「很难」对通过率是同一个信号。 一条 C++ 用例若因缺少头文件而在三个锚点上全部失败，会以 p_hat = 0 的形态被记录为完美难题，污染整个难度分布。本项目已因这一混淆撤回过一次结论。

8.4 技术阻塞点

缺的不是一份语言规格，而是工作区模型。现有评分工作区只有两个文件：待修复文件与测试文件。

Python / JSC++Rust
运行方式解释执行，零配置需编译链接需编译链接
额外必需文件无头文件、CMake 配置、依赖库Cargo.toml、crate 依赖、模块树
单文件可运行是基本不可基本不可
依赖闭包难度已量化：导入不可满足的 16 条用例全部未通过门禁显著高于 Python，且失败发生在编译期而非导入期

8.5 支持一门编译型语言需要同时解决三件事

  1. 可复现的工具链：本机与 CI 必须安装同版本编译器。版本漂移会直接破坏已有测量的可比性。
  2. 工作区从两文件扩展为可构建项目：需要生成最小构建配置，并保证参考解版本一定能编译通过——否则效度门禁会把编译失败误判为用例无效。
  3. 依赖闭包：把会话读取过的兄弟文件一并放入用例。所需快照数据已在抽取阶段获得，尚未使用。

8.7 建议的讨论顺序

  1. 当前 31 条用例的结论是否已足够支撑既定目标？若是，扩容优先级下降。
  2. 若需扩容，方案 B 代价最低且风险已量化，是否先行验证其实际收益？
  3. 若必须覆盖编译型语言，能否接受「评分工作区允许联网获取依赖」这一前提的改变？该前提目前用于保证可复现性。
  4. 工具链版本如何锁定，才能使他人复现结果时不因编译器差异得到不同结论？
