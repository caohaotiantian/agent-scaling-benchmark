Agentic Scaling Benchmark 结果表设计报告

本报告沉淀当前 Agentic Scaling 项目的 Benchmark 结果呈现方案，用于统一比较 SWE-Bench、算子生成、 漏洞挖掘、AI 辅助编程、Arena-style 编程评测等任务上的不同算法策略。

主表：同一 Benchmark 下横向比较算法 综述表：不超过 10 列，面向汇报 通用表：一级列 + 细分列，面向实验归档 支持确定性与偏好型评测

一、设计结论

Benchmark 应当作为统一评测协议存在，不应被算法拆散。不同算法只是在同一个 Benchmark、同一个 case set、 同一套资源与预算口径下生成不同实验行。

核心设计： 一行结果代表“同一 Benchmark + 同一 case set + 一个算法配置 + 一个预算档位 + 一次实验或一组 seed 聚合结果”。 Baseline、投机执行、多模型组合、Best-of-N、Verifier rerank 都进入同一张通用结果表。

面向汇报

使用“项目效果综述表”，保留算法名称、Agent与模型、Benchmark、Case数、主指标、耗时、Token 和相对基线收益。 列数控制在 10 列以内，适合放进周报、PPT 或项目总览页。

面向实验

使用“通用结果总表”，保留完整一级列和细分列。该表适合自动从 summary.json、 results.jsonl、trace 和 sandbox 事件中聚合生成。

二、背景与目标

当前项目希望使用 SWE-Bench 通用软件工程修复、Cann-Bench 算子生成、漏洞挖掘等任务作为 Agentic Scaling 的核心 Benchmark。 这些任务具备明确的成功或失败标准，适合用 resolved rate、pass rate、compile/correct/perf pass 等确定性指标。

但 Agentic Scaling 项目的算法目标不只是提高通过率，还包括验证投机、多模型组合、并行采样、Verifier/Selector、 Retry 策略等是否真正带来质量提升、成本下降、耗时下降或资源效率提升。因此结果表必须覆盖质量、时间、Token、模型调用、 工具调用、沙箱资源、Retry、错误归因和分支选择质量。

此外，AI 辅助编程类任务可能没有完全量化的“正确答案”。这类任务仍然可以进入同一套 Benchmark 表，只是主指标从 成功率 转为 win_rate、Elo、human_accept_rate、 mean_rating 或其他偏好型指标。

本报告参考了 PR39 中已有的 Fusion API timing、trace viewer、SWE-Bench 聚合字段与 usage accounting 思路， 并将其扩展为项目级统一报告设计。参考链接： https://gitcode.com/mindspore/mindspore-factory/pull/39

三、统一数据粒度

人看的报告不需要展开每个 step，但机器落盘必须保留足够细的事件粒度。推荐数据层级如下。

Tool/Sandbox Event event_id 工具执行、容器启动、资源队列与超时分析 tool type、exit code、duration、sandbox start、image pull

六、关键指标口径

1. 主指标

所有 Benchmark 都必须提供 主指标名称 和 主指标值。确定性任务通常使用 resolved_rate 或 pass_rate，偏好型任务可以使用 win_rate、 Elo、accept_rate 或 mean_rating。

2. Oracle 与选择命中

对 best-of-N、投机、多模型组合这类多分支算法，必须区分 Oracle成功率 和 最终成功率。 如果某个分支成功但 selector 没有选中，说明生成能力足够但选择策略失败。

3. 时间拆解

Agent LLM端到端耗时 是客户端 HTTP 视角；Server Wall 是服务端收到请求到响应 ready； Fusion内部模型耗时总和 是 provider call latency 求和；Fusion内部关键路径耗时 才更接近并发下的墙钟解释。

4. Token 与成本

Token 必须区分总量、平均每 case、平均每成功 case。多模型组合还要按 role 拆成 panel、aggregator、verifier、draft、main， 否则无法判断成本主要来自哪里。

5. Retry 与错误归因

Retry 需要同时统计次数和恢复效果。错误归因建议固定为模型推理失败、Agent协议失败、工具执行失败、沙箱基础设施失败、 LLM服务失败、Verifier选择失败、预算耗尽失败等类别。

七、确定性任务与 Arena-style 任务如何共用表

SWE-Bench、算子生成、漏洞挖掘具备明确正确性标准，适合二元成功指标。AI 辅助编程、代码助手体验、IDE Agent 等任务 可能没有唯一标准答案，但仍然可以通过偏好判分或人工接受率进入同一张表。

任务类型 典型任务 评判类型 推荐主指标 是否填写成功率
确定性正确性任务 SWE-Bench、算子生成、漏洞挖掘 确定性判分 resolved_rate、pass_rate、full_pass_rate 填写
半确定性生成任务 代码补全、测试生成、修复建议 自动判分 + 人工采纳 execution_pass_rate、human_accept_rate 按阈值定义后填写
偏好型助手任务 AI 辅助编程、IDE Agent、复杂开发协作 偏好判分 / Arena win_rate、Elo、mean_rating 可为空或映射为胜率

Arena-style 映射

Arena-style 评测可以填入当前表，只是主指标不是准确率，而是相对偏好。推荐映射如下。

通用字段 Arena-style 填法
Benchmark名称 AI Coding Arena 或内部 Arena 名称
Case数量 prompt/task 数，或 pairwise battle 的 unique task 数
评判类型 偏好判分、人工评审 或 人工+模型混合评判
主指标名称 win_rate、Elo、arena_score
主指标值 例如 57.2% win_rate 或 Elo 1124
相对基线胜率 当前系统相对 baseline 的 pairwise win rate
置信区间 bootstrap CI 或多轮评审方差
评判一致性 多人评审一致率、模型 judge 一致率、Kappa 等

八、推荐落盘结构

报告表建议由机器可读事件文件自动生成，避免人工填表造成口径漂移。 

runs/<benchmark>__<timestamp>/
├── run_manifest.json
├── summary.json
├── report.md
├── report.html
├── results.jsonl
├── attempts.jsonl
├── steps.jsonl
├── model_calls.jsonl
├── tool_calls.jsonl
├── sandbox_events.jsonl
└── cases/<case_id>/
    ├── result.json
    ├── attempts/<attempt_id>.json
    ├── trajectory.json
    ├── patch.diff
    ├── grader_report.json
    └── logs/

summary.json 聚合出综述表和通用结果总表，明细文件则用于 Trace Viewer、失败归因和后续统计检验。

九、落地建议

  • 第一阶段：固化 run_manifest.json、summary.json、results.jsonl，生成综述表和通用结果总表。
  • 第二阶段：补齐 attempts.jsonl，支持 best-of-N、投机和多模型组合的 Oracle 与选择命中分析。
  • 第三阶段：补齐 model_calls.jsonl、tool_calls.jsonl、sandbox_events.jsonl，支撑成本、时间和资源归因。
  • 第四阶段：对 AI 辅助编程和 Arena-style 任务增加 评判类型、主指标名称、主指标值、评判一致性 字段。
  • 第五阶段：把 Excel、HTML、Markdown 和前端 Dashboard 都从同一份机器数据生成，避免口径分叉。
最终判断： 当前表设计适用于 SWE-Bench、算子生成、漏洞挖掘这类确定性 Benchmark，也适用于 AI 辅助编程和 Arena-style 评测。 关键是把“准确率”升级为“主指标”，并在表里显式记录评判类型和主指标名称。
